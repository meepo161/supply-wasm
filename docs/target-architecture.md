# Целевая архитектура ERP / WMS / Chat / Task Manager / Mail

Статус: проектное решение по [ТЗ](ТЗ_ERP_WMS_CHAT_TASK_MANAGER.md) и [журналу принятых решений](decisions.md). Код сейчас остаётся [стартовым примером](architecture.md). Этот документ определяет границы реализации, а не заявляет о готовых функциях.

## Зафиксированные решения

| Область | Решение |
| --- | --- |
| Сервер | Kotlin, Ktor, модульный монолит |
| Веб-клиент | Kotlin/Wasm, Compose; существующий JS-таргет допустим как вспомогательный, но не заменяет Wasm |
| Данные | PostgreSQL; jOOQ для типобезопасного доступа |
| Внедрение зависимостей | Koin в отдельных точках сборки клиента и сервера |
| Источник истины | Сервер и PostgreSQL; клиентское состояние не проводит учётные операции |
| Почта | Только общие ящики подразделений; IMAP/SMTP, без независимого архива или связей писем с бизнес-объектами |
| Размещение первой версии | Собственный сервер предприятия в локальной инфраструктуре; удалённый доступ сотрудников не входит в обязательный первый релиз |
| Вход первой версии | Локальные учётные записи ERP с логином/паролем; будущий внешний провайдер идентификации не должен требовать переписывания бизнес-прав |
| Будущий складской клиент | Отдельное Android-приложение через WMS API; Kotlin + Jetpack Compose предложены как технологический вариант |

Способ защищённого удалённого доступа, файловое хранилище, доставка событий и миграционный инструмент ещё требуют отдельного решения. Показатели SLA, RPO/RTO и одновременной нагрузки из ТЗ не заданы численно; исходный ориентир — около 70 сотрудников и 5–10 подразделений.

## Контексты и владельцы данных

Единые справочники не дублируются в функциональных разделах. Каждый контекст владеет записью своих сущностей; остальные хранят стабильные ссылки и получают данные через сервисы/запросы, а не меняют чужие таблицы напрямую.

| Контекст | Владеет | Основные связи |
| --- | --- | --- |
| Доступ и организация | Пользователи, подразделения, роли, права, делегирование | Все действия и области доступа |
| Проекты и задачи | Проекты, этапы, риски, задачи, зависимости, время | Чаты, документы, BOM, потребности |
| Chat | Личные и групповые чаты, участники, сообщения, реакции, прочтение | Единые пользователи и уведомления; не управляет задачами |
| Task Chat | Сообщения и системные события обсуждения конкретной задачи | Состав участников и права получает из Tasks; история отображается в задаче |
| Mail | Подключения общих ящиков подразделений, доступ сотрудников, IMAP-синхронизация, SMTP-отправка | Независим от задач, проектов, закупок и Documents |
| НСИ и изделия | Номенклатура, единицы, изделия, версии BOM, аналоги | WMS, обеспечение, производство |
| Снабжение | Потребности, заявки, предложения, заказы, поставки, претензии | BOM, проекты, складская приёмка |
| WMS | Склады, ячейки, партии, серии, резервы, документы и движения | Поставки, задачи, производственные заказы |
| Производство и качество | Производственные заказы, операции, проверки, несоответствия | BOM, складские выдачи, документы |
| Документы и согласования | Карточки/версии файлов, маршруты, решения | Любой бизнес-объект |
| Платформенные службы | Уведомления, аудит, поиск, отчёты, нумераторы | События и разрешённые данные всех контекстов |

Сквозной процесс: проект → задача и обсуждение → версия BOM → потребность → заявка и заказ → поставка → приёмка → склад и резерв → выдача → производство и качество → закрытие. Связи должны вести к первичным записям, включая основание и историю. Mail обслуживает общие ящики подразделений и в этот процесс автоматически не включается.

## Модули и зависимости

На первом этапе используем существующие четыре Gradle-модуля; внутри сервера разделяем контексты пакетами. Выделение новых Gradle-модулей возможно после появления проверенных границ и циклов изменений.

```text
:app:webApp ──> :app:shared ──> :core <── :server
      │                │                         │
      │                └── HTTP / API ──────────┘
      └── запуск Koin и ComposeViewport

будущий :app:warehouseAndroid ──> WMS API ──> :server

:server: api → application → domain
                  │             ↑
                  └→ ports ← infrastructure (jOOQ → PostgreSQL)
```

HTTP на схеме — взаимодействие во время выполнения, а не Gradle-зависимость. `:core` содержит только действительно общие контракты: идентификаторы, DTO, коды ошибок и типы пагинации. Серверная доменная модель, jOOQ-записи и правила доступа не экспортируются в браузер. Веб-клиент не обращается к PostgreSQL.

Будущий Android-клиент также использует авторизованный WMS API и не подключается к PostgreSQL. Android-модуль и таргет в текущем Gradle-проекте отсутствуют. При его добавлении общие контракты должны быть доступны Android, а серверные правила и хранение останутся на JVM-сервере.

Рекомендуемое размещение:

```text
core/src/commonMain/.../contract/{identity,project,task,chat,stock,...}
app/shared/src/commonMain/.../{feature,api,di,designsystem}
app/shared/src/wasmJsMain/.../platform
app/webApp/src/webMain/.../main.kt
server/src/main/.../{api,application,domain,infrastructure,di}
server/src/main/.../infrastructure/{persistence,files,events}
server/src/main/.../mail/{api,application,imap,smtp,sync}
```

В сервере пакеты контекстов содержат собственные `api`, `application`, `domain` и `infrastructure`. Общие платформенные компоненты (права, аудит, транзакции) имеют единые интерфейсы. Межконтекстные команды вызываются через application-порты, чтобы избежать циклических зависимостей.

## Chat, Task Chat и Mail

Chat обслуживает общение сотрудников. Task Chat является отдельной предметной границей обсуждения задачи, хотя инфраструктура хранения и доставки сообщений может быть общей с Chat. Для каждой задачи контекст обсуждения доступен автоматически. Доступ к истории имеют исполнитель, соисполнители, наблюдатели, инициатор и проверяющий; для задачи подразделения — также все сотрудники подразделения, для проектной — все участники проекта. При добавлении участника история открывается. При удалении доступ прекращается, если у пользователя не осталось другого основания. Просмотр не даёт права редактировать задачу. История сообщений и событий не удаляется. Проверка всегда серверная, в том числе при прямой ссылке и активном соединении доставки сообщений.

Задача может относиться к проекту, подразделению либо быть личным поручением; проект не является обязательным родителем. Область задачи хранится явно и не выводится из пустого `project_id`; связи с проектом и подразделением соответствуют выбранной области. Тип работы обязателен независимо от области и определяет необходимость отдельной приёмки. Личное поручение сотрудник создаёт себе, а руководитель или уполномоченный сотрудник может назначить другому. После закрытия задача и Task Chat переходят в режим только для чтения: новые сообщения, файлы и изменения состава участников запрещены. Для продолжения работы уполномоченный пользователь повторно открывает задачу с указанием причины. Конкретную матрицу типов и правила назначения проверяющего ещё нужно утвердить.

Состав минимальной карточки первой поставки утверждён в [приложении N к ТЗ](ТЗ_ERP_WMS_CHAT_TASK_MANAGER.md) как MVP-02. У задачи один основной исполнитель до начала исполнения; проверяющий обязателен только для типов с отдельной приёмкой и отличается от исполнителя. Обязательность срока, результата, критериев приёмки и данных блокировки проверяется сервером на соответствующих командах. Вложения проверяются отдельно, значимые изменения и причины решений сохраняются в истории, а версия записи обнаруживает конкурентное редактирование. Подзадачи, этап проекта, зависимости, чек-листы, теги, трудоёмкость, фактическое время, повторение и шаблоны в первую поставку не входят; это не отменяет их целевую поддержку. Статусы, переходы и полная матрица полномочий остаются отдельным решением.

Mail — встроенный клиент общих ящиков подразделений. IMAP-адаптер читает письма и синхронизирует папки/флаги; SMTP-адаптер отправляет. Сервер почты остаётся источником письма и вложений; PostgreSQL может хранить настройки доступа, идентификаторы ящиков, курсоры синхронизации и аудит, но не самостоятельный архив содержимого. Несколько сотрудников могут работать с одним ящиком по разрешениям. Mail не создаёт задачи, не привязывает письма к проектам/закупкам и не переносит вложения в Documents.

Фоновый механизм синхронизации и отправки, способ хранения учётных данных и поведение при изменениях на IMAP-сервере проектируются перед реализацией Mail. Это не основание расширять его бизнес-функции. Внешний почтовый сервер подключается через готовые протокольные библиотеки; собственный IMAP/SMTP-сервер в ERP не нужен.

## Доставка и интерфейс

Сообщения чатов приходят без перезагрузки страницы. История хранится на сервере; после потери соединения клиент запрашивает пропущенные сообщения по серверному курсору и повторно проверенным правам. WebSocket — рекомендуемый транспорт, окончательный выбор фиксируется после проверки поведения в целевых браузерах и инфраструктуре. Уведомления показываются в центре ERP и через браузерный механизм при наличии разрешения пользователя. По умолчанию браузерное уведомление нейтрально; без персонального предпросмотра текст сообщения и названия бизнес-объектов не передаются в push-данных. Переход к содержимому требует входа и повторной проверки прав.

Поведение интерфейса утверждено в [приложении M к ТЗ](ТЗ_ERP_WMS_CHAT_TASK_MANAGER.md). После входа открывается единая главная, содержимое которой зависит от прав, участия и назначенных действий, а не только от названия должности. Показатели ведут к первичным записям и не отображаются без методики расчёта. Левое меню и быстрые действия показывают только реализованные и разрешённые функции; избранное персонально и не сохраняет видимость записей после отзыва доступа. Глобальный поиск в верхней панели охватывает сообщения и остальные реализованные типы объектов без утечки через результаты или их количество.

Таблица является основным представлением проектов и задач. Канбан задач входит в первую полноценную версию Task Manager, но не блокирует первый сквозной сценарий; его перетаскивание вызывает разрешённые бизнес-команды. Календарь, Гант и канбан проектов относятся к более поздним этапам. Карточка проекта имеет обзор и вкладки. В задаче описание и обсуждение располагаются рядом на широком экране и во вкладках на телефоне; системные события отличаются от сообщений, а после закрытия обсуждение доступно только для чтения.

Основной интерфейс рассчитан на настольный браузер и адаптируется для телефона: уведомления, чаты, просмотр задач, комментарии, согласование и приёмка. Мобильное решение допускается после сводки при доступности полного комплекта материалов и выполнении обязательных проверок; команда привязывается к версии объекта и документов и повторно проверяется сервером. Для устройств кладовщиков нужны быстрый поиск номенклатуры, приёмка, перемещения, выдача и инвентаризация. Фирменный ориентир — avem.ru, но ERP использует собственные компоненты для плотных рабочих данных; мобильная и складская работа не должна требовать настольной ширины экрана.

Отдельное Android-приложение склада — следующий этап. Уже сейчас WMS API должен поддерживать авторизацию мобильных клиентов и все складские команды. Для номенклатуры предусматриваем несколько штрихкодов с однозначным разрешением к позиции и при необходимости упаковке/единице. Ввод со встроенного или Bluetooth-сканера, включая режим клавиатуры, остаётся на стороне будущего клиента; проверка операции и прав — на сервере. Граница между складскими сценариями в адаптивном веб-интерфейсе и будущем Android-клиенте требует уточнения.

Новая ERP начинает работу с чистой базой: данные 1С и Битрикс не переносятся. Пользователи, оргструктура, номенклатура, склады и бизнес-объекты создаются заново. Начальный остаток появляется только через документированный ручной ввод по результатам фактической инвентаризации.

## Запросы, команды и Koin

Экран Compose получает состояние и отправляет намерение в модель экрана. API-клиент отправляет типизированный запрос. Ktor аутентифицирует запрос, проверяет права на действие и конкретную запись, валидирует ввод и вызывает сценарий. Сценарий проверяет переход состояния, выполняет изменения в транзакции и записывает аудит. Ответ содержит новые данные или стабильный код ошибки.

Бизнес-переходы выражаются командами (`approve`, `post`, `reserve`, `issue`, `sendForReview`), а не произвольной записью поля `status`. Изменяемые карточки имеют версию для обнаружения конкурентной правки. Повтор критичной команды не должен создавать второе проведение. Ошибки различают валидацию, отсутствие доступа/записи, конфликт версии, недопустимый переход, недостаточный остаток и технический сбой.

Koin запускается в `:app:webApp` до создания UI и в Ktor при старте сервера. Контейнеры независимы. Модули регистрируют адаптеры, сценарии и модели экранов; доменные классы получают зависимости через конструктор и не вызывают Koin. В тестах инфраструктурные реализации заменяются тестовыми. Версия Koin добавляется в каталог версий при внедрении после проверки совместимости с Kotlin `2.4.21` и Wasm; поддержка Wasm в [документации Koin](https://github.com/insertkoinio/koin/blob/main/docs/reference/koin-mp/kmp.md) помечена экспериментальной.

## PostgreSQL, jOOQ и складской учёт

Схема создаётся воспроизводимыми версионированными миграциями. jOOQ-код генерируется из схемы и используется только в инфраструктурном слое сервера. База обеспечивает внешние ключи, уникальность, обязательные поля и допустимые диапазоны там, где это возможно. Стабильный внутренний ID отделён от бизнес-номера. У изменяемых записей есть автор, время и версия.

Складские движения — проверяемый журнал первичных операций. Остаток может храниться как оптимизированная проекция, но сверяется с движениями. Проведение документа, изменение движения и актуального остатка, изменение резерва и запись аудита входят в одну транзакционную границу. Конкурентное резервирование/выдача блокируется на уровне нужной учётной позиции или эквивалентной транзакционной стратегией; конкретный способ выбирается после проектирования ключа остатка. Нельзя выдать карантин или брак, дважды провести документ либо получить отрицательный доступный остаток без разрешённого исключения. Проведённые операции исправляются корректирующими документами, не удалением.

Версия BOM после утверждения неизменяема; изменение создаёт ревизию. Расчёт потребности фиксирует использованную версию и основание. Частичные поставки и приёмки сохраняют связь с позицией заказа и потребностью. Количество хранится с точностью, определённой единицей измерения и правилами пересчёта.

Подтверждены два основания снабжения материалами: конкретный проект и задел ведущего инженера — запас материалов предприятия для будущих проектов. Перечни планируются ответственными инженерами по направлениям, но физический остаток принадлежит предприятию и учитывается на общем складе. Закупка задела требует утверждения уполномоченного руководителя. При выделении материалов проекту создаётся резерв без физической выдачи и сохраняется история основания, количества и решений. **Потребность** утверждена как центральный объект процесса: у неё стабильный номер и история; она связывает основание, закупки, поставки, приёмки и резервы. Одна потребность может покрываться несколькими поставками, а одна закупка — несколькими потребностями; связи не ограничиваются один-к-одному.

Любой сотрудник может предложить позицию для задела; предложение не даёт права разместить заказ. Инициатор потребности выбирает предпочтительное предложение поставщика, а уполномоченный снабженец оформляет заказ после согласований по порогам. Резерв возможен под проект, задел, производственный заказ, ремонт и задачу подразделения; он уменьшает доступное количество, но не физический остаток, и не может превышать доступное количество. На первом этапе приёмка не требует обязательного ОТК для всех материалов: кладовщик сверяет позиции и количество, проводит документ, после чего обновляется учётный остаток. Категорийные правила качества предстоит определить отдельно.

## Проект, изделие и производственный заказ

Пять типов проектов, открытие решением уполномоченного руководителя и границы этапов зафиксированы в [приложении J к ТЗ](ТЗ_ERP_WMS_CHAT_TASK_MANAGER.md). Проект может включать несколько моделей изделий и производственных заказов; модель повторно используется в разных проектах. Типовая модель, утверждённая ревизия состава/документации и физический экземпляр с серийным номером — разные сущности. Точная связь ревизии изделия, BOM и пакета документов ещё требует схемы версионирования.

Производственный заказ фиксирует модель и утверждённую ревизию BOM, плановое и фактическое количество. Он может выпускать одну единицу либо партию. Карточка каждого экземпляра создаётся при фактическом завершении его изготовления: партия из десяти единиц порождает десять карточек с уникальными серийными номерами. Изменение BOM не переключает начатый заказ автоматически; решение с оценкой влияния и новой ревизией сохраняется в истории.

Инженерное изменение не запускает автоматические складские списания/замены. Инженер, снабжение, склад, производство и руководитель проекта оценивают последствия; уполномоченное лицо определяет судьбу каждой позиции. Материальные действия выполняются через WMS. Исполнитель испытаний фиксирует протокол, замечания и результат, технический приёмщик подтверждает решение под персональной учётной записью ERP с аудитом. «Не годно» или незакрытые критические замечания блокируют отгрузку; разрешённые отклонения документируются. Закрытие заказа само по себе не открывает отгрузку. Конкретные носители полномочий ещё назначаются руководством предприятия.

Инженерная и производственная специфика, видимая на официальном сайте предприятия, сопоставлена с ТЗ в [карте процессов](production-process-map.md). Утверждённая целевая модель ещё требует проверки на реальных примерах проектов и маршрутах подразделений.

В [приложении L к ТЗ](ТЗ_ERP_WMS_CHAT_TASK_MANAGER.md) утверждены семь целевых правил: раздельные настраиваемые полномочия, персональное подтверждение техприёмки с аудитом, классификация замечаний и разрешение отклонений, независимые ревизии BOM/КД/ПО и фактическая конфигурация экземпляра, неизменяемые утверждённые версии документов, типовые и ручные маршруты, отдельные настраиваемые контрольные списки закрытия заказа и отгрузки. Правила реализуются поэтапно. Конкретные должности, критерии замечаний и матрицы обязательных документов ещё утверждаются внутри предприятия.

## Доступ, файлы и события

Роли являются настраиваемыми шаблонами. Разрешение учитывает действие, тип и запись, проект, склад и подразделение; делегирование имеет срок и область полномочий. Сервер проверяет права при каждом запросе, включая поиск, экспорт, историю, чат и отдельное скачивание файла. UI скрывает недоступные действия только для удобства. Аудит хранит фактического исполнителя и режим замещения.

Версии документов и вложения хранятся с метаданными и проверкой доступа. Ссылка ведёт на карточку документа, не на временный адрес файла. Сообщение всегда показывает автора; системное событие отделено от человеческой реплики. Для уведомлений, поиска и аналитических проекций используем события после фиксации основной транзакции; способ надёжной доставки нужно выбрать отдельно. Отчёты и панели показывают только разрешённые данные и ведут к исходным записям.

## Проверка архитектуры

- Модульные тесты: переходы задач, проектов и BOM; расчёт потребности; права и делегирование.
- Интеграционные тесты с PostgreSQL: миграции, jOOQ-запросы, проведение, журнал движений, резервы и конкурентные операции.
- API-тесты: прямые ссылки без прав, конфликты версий, повтор команд, ошибки и пагинация.
- Сквозные тесты: потребность → закупка → частичная приёмка → резерв → выдача; задача → обсуждение → приёмка.
- Производственные тесты: партия создаёт по одной карточке на фактически завершённый экземпляр; серийные номера уникальны; смена ревизии требует решения; инженерное изменение не меняет склад автоматически; «не годно» и критические замечания блокируют отгрузку.
- Эксплуатационные проверки: восстановление БД и файлов, нагрузка после задания целевых показателей.

До промышленного складского учёта необходимы транзакционная целостность, аудит и серверные права. Порядок этапов и открытые вопросы приведены в [плане внедрения](implementation-plan.md).
