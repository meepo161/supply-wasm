### Что работает корректно (подтверждено сценариями)

- Цикл «потребность → согласование → предложение → выбор → заказ → согласование → отправка → частичная приёмка → остаток → ожидаемые поставки» сходится по количествам. Самосогласование потребности и заказа запрещено (403).
- Резерв → выдача → подтверждение: повторное «Подтвердить» с тем же ключом идемпотентности не списывает дважды; возврат сверх выданного отклоняется; резерв из карантина запрещён.
- BOM: утверждённую ревизию нельзя править, where-used работает, потребность из BOM считает количество × выпуск, материалы заказа инициализируются из BOM.
- Задачи: посторонний не видит задачу, её чат и сводку проекта; самоприёмка запрещена; устаревшая версия даёт 409.
- Деактивация сотрудника сразу обрывает его сессию; кадровик не может создать роль `*:*`; после сброса пароля старый не работает; после 10+ неудачных попыток входа срабатывает 429.
- Сотрудник без прав не видит чужие проекты, задачи и объекты в списках, поиске, календаре и сводке аналитики; закрытые разделы меню закрыты и на сервере (403).
- Все 332 маршрута требуют сессию (401 для анонима), кроме явно публичных.

Настоящие сбои сервера по-прежнему дают 500 (например, откат транзакции вложений в `AttachmentMessageRoutesTest`). ## Инфраструктура тестов

- **TEST-01.** Порт тестовой БД был зашит в 38 тестовых файлах (`localhost:5433`). На машине разработчика 5433 занят PostgreSQL от КОМПАС-3D, а контейнер ERP поднят на 5434 (`.local/postgres-compose.yml`). Исправлено в ветке: `TestDatabase.TEST_URL` читает `ERP_TEST_DB_PORT` (по умолчанию 5433, CI не затронут).
- **TEST-02.** Вспомогательные функции (`createUserWithRole`, `loginClient`, `testApp`, `stringify`) скопированы почти в каждый из 40 тестовых классов. Новые smoke-тесты используют общий `SmokeSupport.kt`; старые стоит перевести на него постепенно.
- **TEST-03.** `TestDatabase.reset()` перечисляет таблицы вручную; таблицы V37–V42 (`task_dependencies`, `delegations`, `counterparties` и др.) очищаются только каскадом от `users`. Новая таблица без FK на очищаемые таблицы будет «протекать» между тестами.
- **TEST-04.** Полный `:server:test` идёт больше часа из-за WebSocket-тестов с реальными ожиданиями. Smoke-набор занимает около 2,5 минут и подходит для быстрой проверки перед сдачей.

## Сверка полей счёта поставщика (пример: счёт ОАО «СЗТТ» № 219658 от 25.02.2025)

Отдельной сущности «Счёт на оплату» в системе нет. Данные счёта распределены между предложением поставщика (`SupplierOffer`), заказом (`PurchaseOrder.invoiceNo`), приёмкой (основание `INVOICE` + номер/дата документа) и карточкой поставщика.

| Поле счёта | Где у нас | Статус |
| --- | --- | --- |
| Номер счёта | `PurchaseOrder.invoiceNo`, `Receipt.sourceDocumentNo` | есть |
| **Дата счёта** | только у приёмки (`sourceDocumentDate`); у заказа нет | частично |
| **Срок действия счёта** (7 банковских дней) | у предложения `validUntil` (календарная дата); у заказа нет | частично |
| Поставщик: наименование, ИНН, КПП, адрес, телефон | `SupplierDto.name/inn/kpp/legalAddress/phone` | есть |
| **Банковские реквизиты**: банк, БИК, р/с, к/с | нет ни в одной сущности | **нет** |
| Покупатель (наши реквизиты: ООО «АВИААГРЕГАТ-Н», ИНН/КПП, адрес) | справочника собственной организации нет | **нет** |
| Назначение платежа («Оплата по заказу клиента №219658») | нет | **нет** |
| Строка: № п/п | `lineNo` | есть |
| **Код товара поставщика** (10000185984) | нет; есть только наш `nomenclatureCode` | **нет** |
| Наименование, количество, ед. изм. | через номенклатуру и строку | есть |
| Цена без НДС, ставка НДС, сумма | `unitPrice`, `vatRate`, `lineTotal` | есть |
| **Сумма НДС по строке** | только итог по документу (view `*_totals`) | частично |
| Итого / НДС / Итого с НДС | `totals.netTotal/vatTotal/grossTotal` | есть, формулы совпадают со счётом: 23 360,00 / 4 672,00 / 28 032,00 |
| Сумма прописью | нет (нужна для печатной формы) | нет |
| **Кратность поставки** (ТОП/ТШП кратно 3) | `nomenclature.order_multiple` (V41) есть, но в предложении и заказе не проверяется | частично |
| Условия оплаты (100 % предоплата) | `paymentTerms` — свободный текст; процента предоплаты и графика оплат нет | частично |
| Срок изготовления (25 рабочих дней) | `deliveryDays` (без разделения рабочих и календарных дней) | частично |
| Условия доставки (до ТК «Деловые Линии», тариф за покупателем) | `SupplierOffer.deliveryTerms`, `deliveryCost` | есть в предложении, в заказ не переносится |
| Ответственный менеджер поставщика, телефон, доб. | `supplierContactName/Channel` в предложении | есть |
| Файл счёта (PDF) | можно приложить документом типа `INVOICE` в «Документах», но связи со строками заказа нет | частично |

Расхождение с реальным процессом: сейчас приёмку с основанием «Счёт на оплату» создаёт **кладовщик** во вкладке «Склад» и вводит номер счёта текстом, без файла. На предприятии счёт загружает и поступление по нему оформляет **снабжение**, а склад только физически принимает товар. Проект исправления — `docs/plans/2026-11-22-supplier-invoice-design.md`.

Риски расчёта:

1. НДС считается в базе как `SUM(line_total × rate / 100)` с точностью до 4 знаков без округления по строкам до копеек. Для «круглых» цен, как в этом счёте, итоги совпадают. При ценах вроде 33,33 сумма НДС может разойтись со счётом поставщика на копейки.
2. Цены «в т. ч. НДС», которые поставщики выставляют часто, и вариант «Без НДС» (это не то же, что 0 %) представить нельзя.

Для работы бухгалтерии и оплаты как минимум не хватает: даты и срока счёта в заказе, банковских реквизитов поставщика, справочника собственной организации, кода товара поставщика и проверки кратности. Это предложения: реализация требует отдельного решения пользователя.
