# Техническое задание: ERP / WMS / CHAT / TASK MANAGER

## Единая корпоративная система ООО «Авиаагрегат-Н»

**Версия:** 1.0\
**Дата:** 13.11.2026\
**Статус:** функциональное ТЗ для проектирования и поэтапной разработки.

## 1. Назначение и цель

Разработать единую информационную систему предприятия, объединяющую
управление проектами, задачами, коммуникациями, складом, снабжением,
номенклатурой, составом изделий (BOM), производственными заказами,
документами, согласованиями и аналитикой.

Цель --- обеспечить сквозной процесс от возникновения потребности до
выполнения работ и получения результата. Данные должны быть связаны
между собой, иметь историю изменений, ответственных и понятные статусы.

### 1.1. Зафиксированный технологический стек

-   Backend: Kotlin + Ktor.
-   Клиент: Kotlin/Wasm.
-   UI: Compose.
-   СУБД: PostgreSQL.
-   Доступ к данным: jOOQ.

Дополнительные библиотеки, инфраструктурные компоненты, авторизация,
хранение файлов, доставка событий и развёртывание выбираются отдельно.
Основной стек нельзя самовольно менять.

### 1.2. Главный принцип

**Проект → этапы → задачи → обсуждения → документы → BOM → потребности →
закупки → поставки → приёмка → склад → комплектация → производство →
качество → завершение проекта.**

Модули не должны быть изолированными приложениями со своими дублирующими
справочниками пользователей, номенклатуры, проектов и документов.

## 2. Принципы проектирования

1.  Единая модель данных и единый источник истины.
2.  Сквозные связи между проектами, задачами, чатами, документами,
    закупками и складом.
3.  История критичных изменений без бесследного перезаписывания.
4.  Серверная проверка прав и бизнес-правил.
5.  Для каждой сущности --- определённые статусы и разрешённые переходы.
6.  Проведение складского документа и изменение остатков выполняются
    атомарно.
7.  Любой остаток и показатель проверяется по первичным данным.
8.  Интерфейс показывает важную информацию с учётом роли.
9.  Кнопки, отчёты и показатели работают на реальных данных.
10. Проведённые операции исправляются корректирующим документом, а не
    удаляются.

## 3. Пользователи, роли и права

### 3.1. Типовые роли

Системный администратор; администратор предприятия; генеральный
директор; технический директор; руководитель проекта; руководитель
подразделения; конструктор; технолог; инженер-испытатель;
производственный мастер; сборщик/монтажник; снабженец; руководитель
снабжения; кладовщик; руководитель склада; специалист по качеству;
бухгалтер; делопроизводитель; аудитор; внешний пользователь с
ограниченным доступом.

Роли --- шаблоны. Администратор может создавать и изменять роли без
правки исходного кода.

### 3.2. Пользовательская карточка

ФИО, аватар, должность, подразделение, руководитель, рабочие контакты,
логин, состояние учётной записи, роли, дата создания, последняя
активность, рабочий календарь и настройки интерфейса.

### 3.3. Организационная структура

Дерево: предприятие → подразделение → отдел/группа → команда. У
подразделения есть руководитель, участники, описание, родительский узел
и область доступа.

### 3.4. Модель прав

Права настраиваются по модулю, типу сущности, действию, конкретной
записи, проекту, складу и подразделению. Действия: просмотр, создание,
редактирование, удаление черновика, согласование, отклонение,
проведение, отмена/сторно, экспорт, печать, управление доступом.

Проверка прав выполняется сервером на каждом запросе. Скрытие кнопки в
UI не является защитой.

### 3.5. Делегирование

Временное замещение с указанием замещаемого, замещающего, периода,
области полномочий и утвердившего. В аудите видно фактического
исполнителя и режим замещения.

## 4. Главная страница

### 4.1. Персональная панель

Мои задачи на сегодня; просроченные задачи; ожидающие моего действия;
входящие согласования; упоминания и непрочитанные сообщения; мои
проекты; созданные мной заявки; ожидаемые поставки; складские задания;
последние объекты; избранное; быстрые действия.

Блоки настраиваются и зависят от роли.

### 4.2. Панель руководителя

Активные проекты; проекты с риском срыва; просрочки по подразделениям;
загрузка сотрудников; дефициты материалов; закупки в ожидании;
задержанные поставки; проблемные приёмки; незакрытые согласования;
критические задачи.

Каждый показатель открывает список первичных записей, из которых он
рассчитан.

### 4.3. Глобальный поиск

Искать проекты, задачи, сообщения, пользователей, материалы, изделия,
BOM, документы, заявки, заказы, поставки, складские документы,
контрагентов, партии и серийные номера. Результаты группируются по
типам. Поиск не раскрывает объекты без прав.

### 4.4. Быстрое создание

Из любой рабочей области доступно создание задачи, проекта, сообщения,
заявки на закупку, документа, контрагента и складского документа.
Быстрая форма содержит минимум обязательных полей, расширение доступно
после создания.

## 5. Проекты

### 5.1. Карточка проекта

Номер, краткое и полное название, описание, заказчик, руководитель,
участники, подразделение-владелец, даты план/факт, приоритет, статус,
процент готовности, категория, изделия, производственные заказы, BOM,
договоры, документы, риски и теги.

### 5.2. Статусы

Черновик, подготовка, на согласовании, запланирован, в работе,
приостановлен, требует внимания, на проверке, завершён, закрыт, отменён.

### 5.3. Структура и представления

Проект → этап → контрольная точка → задача → подзадача → чек-лист. Для
этапа задаются срок, ответственный, зависимости, критерии завершения и
процент выполнения.

Представления: список, канбан, календарь, диаграмма Ганта, таблица
этапов, панель проекта, журнал событий, риски. Фильтры: руководитель,
участник, статус, приоритет, срок, подразделение, просрочка.

### 5.4. Зависимости

Связи: начало после завершения, начало одновременно, завершение
одновременно, завершение после завершения. Циклические зависимости
запрещены. При переносе срока показывать влияние на последующие задачи.

### 5.5. Риски и изменения

Риск содержит описание, категорию, вероятность, влияние, критичность,
ответственного, план реагирования, срок, статус и связанные объекты.
Изменение объёма, сроков, бюджета или состава изделия оформляется
запросом на изменение с оценкой влияния и решением.

### 5.6. Закрытие

Закрытие требует выполнения обязательных задач либо утверждённых
исключений, передачи документов в архив, обработки остатков и
незавершённых закупок, приёмки результата и итогового отчёта.

## 6. Задачи (Task Manager)

### 6.1. Карточка задачи

Номер, название, описание, инициатор, основной исполнитель,
соисполнители, наблюдатели, проект, этап, родительская задача, даты
создания/начала/срока, приоритет, оценка трудоёмкости, фактическое
время, чек-лист, критерии приёмки, теги, вложения, обсуждение,
документы, зависимости, причина блокировки и результат.

### 6.2. Статусы

Черновик, новая, назначена, принята, в работе, ожидает информации,
заблокирована, на проверке, возвращена на доработку, выполнена, закрыта,
отменена.

### 6.3. Назначение

Один основной исполнитель обязателен для персональной задачи. Для
групповой задачи нужен механизм принятия конкретным сотрудником.
Назначение «всем» без владельца не должно размывать ответственность.

### 6.4. Подзадачи и чек-листы

Иерархия подзадач с настраиваемой максимальной глубиной. Пункт чек-листа
может иметь ответственного, срок и комментарий. Родительская задача
может требовать завершения обязательных подзадач.

### 6.5. Приёмка

Исполнитель отправляет задачу на проверку. Проверяющий принимает или
возвращает с обязательным комментарием. История всех попыток
сохраняется. Самостоятельная приёмка исполнителем запрещена, если
назначен отдельный проверяющий.

### 6.6. Учёт времени и шаблоны

Ручной ввод и таймер. Запись содержит пользователя, задачу, проект,
дату, длительность, категорию и комментарий. Изменения отражаются в
аудите.

Повторение: ежедневно, по рабочим дням, еженедельно, ежемесячно,
ежегодно или по правилу. Шаблон содержит описание, чек-лист, роли
исполнителей, сроки относительно создания, приоритет, этап и документы.

### 6.7. Блокировки и массовые действия

Блокировка требует причины, автора, даты и ответственного за снятие.
Массовое переназначение, перенос сроков, изменение приоритета, теги и
экспорт выполняются с проверкой прав для каждой записи.

## 7. Чаты и коммуникации (CHAT)

### 7.1. Типы чатов

Личные, групповые, проектные, задач, закупочных заявок, поставок,
складских операций, документов, подразделений, общие информационные
каналы и каналы инцидентов.

### 7.2. Сообщения

Автор, дата/время, текст, вложения, упоминания, реакции, ссылки на
сущности, признак редактирования, ответы/цитирование, цепочка
обсуждения. **У каждого сообщения обязательно отображается автор --- имя
и фамилия, при наличии аватар.** Нельзя показывать реплики без понятной
идентификации отправителя.

### 7.3. Возможности

Текст, форматирование, файлы, изображения, ответы, редактирование
собственных сообщений, отзыв с сохранением системного следа, реакции,
@упоминания, закрепление, поиск, переход к связанному объекту,
непрочитанные сообщения, индикаторы доставки/прочтения при поддержке,
отключение уведомлений, избранные чаты, архивирование и пересылка с
указанием источника.

### 7.4. Обсуждение задачи

У каждой задачи есть контекстное обсуждение. В нём отображаются
сообщения и системные события: создание, назначение, смена срока,
изменение статуса, прикрепление файла, блокировка, отправка на проверку
и решение проверяющего.

Системное событие визуально отличается от сообщения человека. Например:
«Иван Петров назначил Анну Смирнову исполнителем» или «Срок изменён с
15.11 на 18.11». У события есть инициатор и время.

### 7.5. Права

Права на чат, историю и каждый файл проверяются отдельно. Нельзя
получить закрытую переписку по прямой ссылке. Удаление участника
прекращает доступ, но не уничтожает историю.

## 8. WMS --- склад

### 8.1. Структура склада

Несколько складов, зоны, помещения, стеллажи, секции, полки, ячейки,
места временного хранения, приёмки, отгрузки, карантина и брака. Ячейка
имеет код, склад, тип, вместимость, ограничения и состояние.

### 8.2. Номенклатура

Код, название, описание, категория, тип, единица измерения, коэффициенты
пересчёта, артикул, производитель, модель, характеристики, масса,
габариты, минимальный и страховой запас, срок поставки,
партионный/серийный учёт, условия хранения, допустимые склады,
изображения, документы, аналоги, штрихкоды и архивный признак.

### 8.3. Остатки

Показывать физический, зарезервированный, доступный, ожидаемый,
карантинный, бракованный и находящийся в пути остаток. Доступное
количество рассчитывается по единому правилу и не должно становиться
отрицательным без утверждённого исключения.

### 8.4. Приход и приёмка

Основания: заказ поставщику, возврат, перемещение, начальный остаток и
прочий документированный источник.

Сценарий: открыть ожидаемую поставку → сверить позиции → указать
фактическое количество → зарегистрировать партии/серийные номера →
зафиксировать расхождения → провести контроль качества → разместить →
провести документ.

Поддержать частичную приёмку и несколько приёмок по одному заказу.

### 8.5. Контроль качества

План контроля задаёт параметры, допустимые значения, метод,
оборудование, ответственного и необходимость протокола. Результаты:
принято, принято с отклонением, карантин, отклонено/брак. Карантин и
брак не доступны для обычной выдачи.

### 8.6. Размещение и перемещение

Система предлагает ячейки с учётом совместимости, вместимости, типа
материала и ограничений. Перемещение поддерживается между ячейками,
зонами и складами. Межскладское перемещение имеет состояния создано,
отправлено, в пути, принято, расхождение, отменено. Материал не может
одновременно числиться доступным на двух складах.

### 8.7. Резервирование

Резерв создаётся под проект, производственный заказ, задачу, ремонт или
внутреннее потребление. Содержит потребность, номенклатуру, количество,
склад, партию при необходимости, срок и владельца. Поддержать частичный
резерв, снятие и историю. При дефиците предложить сформировать
потребность снабжения.

### 8.8. Комплектация и выдача

Проверка доступности → резерв → лист комплектации → отбор по ячейкам →
подтверждение фактического количества → передача получателю →
подтверждение получения → проведение расхода. Поддержать частичную
комплектацию, недостачу, отказ получателя и согласованную замену партии.

### 8.9. Возврат

Возврат связан с исходной выдачей. Указываются возвращающий,
принимающий, количество, состояние, партия/серийный номер, причина и
место размещения. До проверки пригодности возврат не увеличивает обычный
доступный остаток.

### 8.10. Списание

Причины: повреждение, брак, срок годности, потеря, естественная убыль,
технологический расход и прочее. Списание сверх лимита требует
согласования и основания.

### 8.11. Инвентаризация

Полная, по складу, зоне, ячейке или выбранной номенклатуре. Процесс:
задание → фиксация учётного среза → комиссия → подсчёт → повторный
пересчёт спорных позиций → ведомость расхождений → согласование →
корректирующие движения. Определить правила параллельных движений в
инвентаризируемой области.

### 8.12. Партии, серии и штрихкоды

Партия: номер, дата изготовления, срок годности, поставщик, документ
поступления, контроль. Серийный объект: уникальный номер, модель,
поступление, история перемещений, выдач, ремонтов и местонахождение.
Штрихкоды для номенклатуры, партий, серийных номеров, ячеек и
документов. Сканирование не обходит бизнес-проверки.

### 8.13. Отчёты WMS

Остатки на дату, доступные остатки, резервы, дефициты, движения,
карточка учёта, оборачиваемость, залежалые позиции, сроки годности,
партии, серийные номера, расхождения инвентаризации, ожидаемые поставки,
выдачи по проектам, возвраты, списания и загрузка зон.

## 9. Снабжение и закупки

### 9.1. Источники потребности

BOM, производственный заказ, задача, минимальный остаток, заявка
подразделения, ремонт или ручная потребность.

### 9.2. Заявка на закупку

Номер, инициатор, подразделение, проект, основание, требуемая дата,
приоритет, позиции, количество, единица, технические требования,
допустимые аналоги, предпочтительный поставщик, комментарии, вложения,
статус и согласующие.

### 9.3. Жизненный цикл

Черновик → отправлена → на согласовании → уточнение → согласована →
передана снабжению → поиск поставщика → сбор предложений → выбор → заказ
оформлен → ожидается поставка → частично поставлена → поставлена →
закрыта. Также отклонение/отмена.

### 9.4. Проверка перед закупкой

Проверять свободный остаток, резервы, ожидаемые поступления, другие
склады, аналоги и открытые заявки. Предупреждать о возможном дубле
потребности.

### 9.5. Работа снабженца

Очередь заявок с фильтрами по приоритету, сроку, проекту и статусу.
Фиксировать ответственного, дату принятия, поставщиков, запросы,
предложения, цены, сроки, доставку, оплату, сертификаты, документы,
комментарии и причины выбора.

### 9.6. Сравнение предложений

Сравнивать цену, валюту, общую стоимость, срок, доставку, условия
оплаты, гарантию, соответствие техническим требованиям, наличие
документов и срок действия предложения. Нельзя выбирать поставщика
исключительно по минимальной цене без проверки соответствия и сроков.

### 9.7. Согласование и заказ

Маршрут зависит от суммы, проекта, категории, бюджета и подразделения.
Решения: согласовать, отклонить, вернуть, согласовать с условиями.
Существенное изменение после согласования запускает повторное
согласование.

Заказ поставщику содержит поставщика, позиции, цены, количество, сроки,
адрес доставки, условия оплаты, договор/счёт, документы, ответственного
и статус. Поддержать частичные поставки.

### 9.8. Поставщики и претензии

Карточка поставщика: реквизиты, контакты, адреса, категории продукции,
договоры, сертификаты, история заказов, претензии, сроки, оценка и
статус проверки. Оценка строится на фактах: срок, качество,
комплектность, документация, реакция, рекламации и стабильность цены.

Претензия содержит вид проблемы, заказ, поставку, приёмку, партию,
документы, ответственного, решение и итог.

## 10. Номенклатура, изделия и BOM

### 10.1. Типы

Сырьё, материал, покупной компонент, стандартное изделие, собственный
узел, сборочная единица, готовое изделие, инструмент, оборудование,
расходник, услуга и комплект.

### 10.2. Карточка изделия

Код/обозначение, наименование, описание, версия, ревизия, конструктор,
технолог, статус разработки, применяемость, чертежи, ТУ, паспорт,
нормативные документы, связанные BOM и история изменений.

### 10.3. BOM

Иерархическая структура. Строка: родительское изделие, дочерняя позиция,
количество, единица, позиционное обозначение, уровень, обязательность,
тип позиции, комментарий, замены, норма расхода, потери, версия и период
действия.

### 10.4. Версии

Черновик, на согласовании, утверждена, действует, заменена, отменена.
Утверждённая версия неизменяема. Изменение создаёт новую ревизию с
автором, датой, причиной, сравнением и согласованием.

### 10.5. Разузлование и замены

Рассчитывать потребность по всем уровням с учётом количества выпуска,
норм, потерь и выбранной версии. Показывать исходную структуру и сводную
потребность. Аналоги имеют условия применимости, коэффициент и
необходимость согласования. Замена в конкретном заказе не меняет
исходную BOM.

### 10.6. Применяемость

Показывать изделия, проекты и заказы, использующие компонент. Перед
архивированием проверять активные ссылки.

## 11. Планирование обеспечения

Расчёт по BOM учитывает версию, дату потребности, склад, резервы,
ожидаемые поступления, минимальную партию, кратность упаковки, страховой
запас, срок поставки, аналоги и открытые заявки.

По каждой позиции показывать общую потребность, доступное количество,
резерв, ожидаемое поступление, чистый дефицит и рекомендуемую закупку.

Статусы: обеспечено складом, зарезервировано, ожидается по заказу,
заявка создана, требуется закупка, дефицит не закрыт, требуется решение.

При нехватке распределение между проектами выполняется по утверждённым
правилам. Автоматически менять существующие резервы без разрешения
запрещено.

## 12. Документооборот (DMS)

Типы документов: техническое задание, договор, счёт, коммерческое
предложение, заказ, накладная, акт, паспорт изделия, руководство,
чертёж, спецификация, протокол испытаний, служебная записка, приказ,
отчёт, сертификат, фотография и прочее.

Карточка документа содержит номер, название, тип, описание, автора,
владельца, даты, статус, версию, конфиденциальность, срок хранения,
связи, теги, файлы и маршрут согласования.

Замена файла создаёт новую версию. Старая версия сохраняется. Должна
быть определена действующая версия. Ссылки ведут на карточку документа,
а не на временный адрес файла.

Маршруты согласования последовательные или параллельные. Решение
фиксирует пользователя, дату, комментарий и версию документа. Шаблоны
могут заполняться данными проекта, поставщика, изделия и задачи. Поиск
--- по реквизитам, связям, тегам и содержимому, если выбранная
реализация обеспечивает извлечение текста.

## 13. Универсальные согласования

Согласования применяются к закупкам, документам, изменениям BOM,
списаниям, инвентаризациям, проектным решениям и другим объектам.

Маршрут поддерживает последовательные и параллельные этапы, роли,
конкретных пользователей, условия, замещение, сроки реакции и эскалации.

Решения: согласовать, отклонить, вернуть, согласовать с замечаниями,
запросить информацию. Согласующий видит контекст объекта. Существенное
изменение объекта требует новой версии или перезапуска процесса.

## 14. Календарь и загрузка

Единый календарь включает задачи, этапы, контрольные точки, поставки,
согласования, инвентаризации и плановые работы. Рабочие календари
задаются на предприятие, подразделение и пользователя. Учитываются
выходные, праздники и недоступность сотрудников.

Показывать плановую загрузку, конфликты сроков и перегрузку. Плановая
трудоёмкость не смешивается с фактическим временем.

## 15. Производственные заказы

Производственный заказ содержит номер, проект, изделие, версию BOM,
количество, плановые и фактические даты, ответственного, подразделение,
статус, приоритет, маршрут, комплектность, документы и результаты
контроля.

Настраиваемые этапы: подготовка, комплектация, сборка, монтаж,
настройка, испытания, контроль, устранение замечаний, приёмка,
завершение.

Перед запуском этапа проверять обязательные материалы и документы.
Исключение допускается только при наличии прав и фиксации решения.

Фактический расход связывается со складскими документами. Отклонение от
нормы показывается и объясняется. Для серийного изделия хранить номер,
состав фактически использованных компонентов (если требуется
прослеживаемость), даты изготовления и испытаний, ответственных и
комплект документов.

## 16. Качество и несоответствия

Несоответствие регистрируется для материала, поставки, производства,
изделия, документа или процесса. Поля: номер, категория, описание, дата,
автор, обнаруживший, критичность, объект, партия/серия, фотографии,
временные меры и ответственный.

Жизненный цикл: зарегистрировано → оценка → назначен ответственный →
анализ причины → корректирующие действия → проверка эффективности →
закрыто.

Корректирующие действия могут создавать задачи. Закрытие несоответствия
зависит от выполнения обязательных действий.

## 17. Контрагенты (CRM-контур)

Единый справочник заказчиков, поставщиков и подрядчиков. Карточка: тип,
наименование, реквизиты, адреса, контакты, ответственный, категории,
договоры, заказы, поставки, претензии, документы, история и статус.

Контактные лица имеют должность, каналы связи и историю взаимодействия.
Система предупреждает о дублях. Объединение выполняется уполномоченным
лицом с сохранением ссылок.

Полноценная воронка продаж не является обязательной частью первой
очереди и может быть отдельным этапом.

## 18. Уведомления

Единый центр с категориями, фильтрами, отметкой прочтения и переходом к
объекту. События: назначение, срок, упоминание, сообщение, согласование,
изменение проекта, дефицит, заказ, задержка, расхождение, критическая
операция, приближение срока и просрочка.

Пользователь настраивает обычные уведомления. Критические обязательные
уведомления не отключаются без соответствующего права. Предусмотреть
группировку дублей и эскалацию при отсутствии реакции.

## 19. Аналитика и отчёты

### Проекты

Портфель, план/факт сроков, выполнение этапов, просрочки, риски,
загрузка, обеспеченность, изменения и закрытые проекты.

### Задачи

Отчёты по исполнителям, статусам, просрочкам, времени выполнения и
ожидания, возвратам с проверки, блокировкам и подразделениям.

### Склад

Остатки, движение, оборачиваемость, дефициты, резервы,
инвентаризационные расхождения, списания, неликвиды и материалы по
проектам.

### Снабжение

Заявки, длительность обработки, время от заявки до заказа, от заказа до
поставки, просрочки, качество поставщиков, отклонения цен и закупки по
проектам.

### Руководитель

Сводная панель с отклонениями, дефицитами, задержками, согласованиями,
критическими задачами и нагрузкой.

Каждый отчёт показывает период, дату формирования, фильтры и методику.
Агрегат должен открывать исходные записи.

## 20. Импорт, экспорт и печатные формы

Импорт справочников и начальных остатков должен иметь предварительную
проверку: новые и обновляемые записи, дубли, ошибки и неизвестные
значения. Ошибка не должна оставлять базу в частично испорченном
состоянии.

Экспорт учитывает права и фильтры. Экспорт чувствительных данных
фиксируется в аудите.

Печатные формы: карточка номенклатуры, складской ордер, требование на
выдачу, лист комплектации, акт приёмки, инвентаризационная ведомость,
заявка, сравнение предложений, заказ поставщику, паспорт изделия, BOM,
карточка проекта, отчёт задачи, маршрутный лист, протокол контроля.

## 21. Администрирование

Панель: пользователи, роли, права, подразделения, справочники, процессы,
статусы, шаблоны задач, маршруты, уведомления, календари, склады,
нумераторы, аудит, системные события, хранение файлов и сессии.

Нумераторы поддерживают маску с префиксом, годом, подразделением и
последовательностью. Дубликаты при одновременном создании запрещены.

По возможности администратор настраивает статусы, переходы, обязательные
поля, согласования, уведомления и шаблоны без релиза. Критичные учётные
правила остаются контролируемыми и тестируемыми.

## 22. Аудит и безопасность

Аудировать входы, ошибки входа, создание и изменение записей, права,
согласования, складские проведения, списания, корректировки, экспорт,
административные действия и настройки.

Требования: серверная авторизация каждого действия, защита от доступа к
объектам по ID, валидация, безопасная обработка файлов, лимиты вложений,
защита от повторного выполнения команд, контроль конкурентных изменений,
безопасное хранение секретов, управление сессиями.

Доступ к файлу проверяется отдельно от доступа к карточке. Персональные
и финансовые сведения доступны только необходимым ролям. Проведённые
операции, согласования и аудит нельзя физически удалять обычным
пользователям.

## 23. Требования к интерфейсу (UI/UX)

### 23.1. Компоновка

Левая навигация, верхняя панель с поиском, быстрым созданием,
уведомлениями и профилем, центральная рабочая область, контекстная
боковая панель и хлебные крошки.

### 23.2. Разделы

Главная, Мои задачи, Проекты, Чаты, Склад, Снабжение, Номенклатура и
BOM, Производство, Документы, Согласования, Календарь, Контрагенты,
Отчёты, Администрирование.

### 23.3. Таблицы

Серверная пагинация, сортировка, фильтры, поиск, настройка и изменение
ширины колонок, закрепление, сохранённые представления, массовые
действия, экспорт и переход в карточку. При возврате сохранять фильтры и
позицию, если возможно.

### 23.4. Карточки

Заголовок и номер, статус, основные действия, ответственный, ключевые
даты, сводка, вкладки, связи, история, обсуждение и документы. Самая
важная информация находится в верхней части.

### 23.5. Формы

Группировка полей, обозначение обязательности, валидация, ошибки рядом с
полем, сохранение черновика, предупреждение о потере несохранённых
данных. Ошибка сервера не должна сбрасывать введённое.

### 23.6. Обязательные UX-правила

-   основные действия доступны без глубокого поиска;
-   важный статус виден сразу;
-   автор каждого сообщения очевиден;
-   системные события отличаются от реплик;
-   пустые состояния объясняют, что делать;
-   опасные действия требуют подтверждения;
-   интерфейс не теряет введённые данные;
-   длинные названия и большие таблицы отображаются корректно;
-   скрытые обязательные действия недопустимы;
-   UI не показывает фиктивные показатели или кнопки.

## 24. Нефункциональные требования

Производительность, SLA, число пользователей, объём данных, RPO/RTO и
целевые времена ответа уточняются после профилирования и оценки
инфраструктуры. Списки используют серверную фильтрацию и пагинацию.
Загрузка всей истории чатов или всех движений для открытия карточки
недопустима.

Предусмотреть масштабирование, резервное копирование базы и файлов,
регулярную проверку восстановления, мониторинг ошибок и журналирование.
Основной язык --- русский. Форматы дат, времени, чисел и единиц должны
быть единообразны.

## 25. Логическая модель данных

Ключевые сущности:

-   User, Role, Permission, Department, Team.
-   Project, ProjectMember, ProjectStage, Milestone, Risk.
-   Task, TaskAssignee, TaskChecklist, TaskDependency, TimeEntry.
-   Chat, ChatMember, ChatMessage, MessageReaction, Attachment.
-   Warehouse, StorageZone, StorageLocation, Nomenclature, Unit.
-   StockBalance, StockMovement, Lot, SerialItem, Reservation.
-   Inventory, InventoryLine, Receipt, ReceiptLine, Issue, Return.
-   Product, BomRevision, BomLine, Substitute.
-   Demand, ProcurementRequest, ProcurementLine, SupplierOffer.
-   PurchaseOrder, PurchaseOrderLine, Delivery, SupplierClaim.
-   Document, DocumentVersion, ApprovalProcess, ApprovalStep,
    ApprovalDecision.
-   ProductionOrder, ProductionOperation, QualityCheck, Nonconformity,
    CorrectiveAction.
-   Notification, NotificationPreference, AuditEvent.

У каждой сущности стабильный внутренний ID. Бизнес-номер --- отдельное
поле. Для изменяемых сущностей предусмотреть автора и время
создания/изменения, статус и контроль конкурентной версии. Неизменяемые
движения и аудит моделируются отдельно.

Основные связи: проект 1:N этапы; этап 1:N задачи; задача 1:N подзадачи;
чат 1:N сообщения; чат N:M пользователи; проект N:M участники; изделие
1:N версии BOM; версия BOM 1:N строки; заявка 1:N позиции; заказ 1:N
поставки; поставка 1:N приёмки; склад 1:N ячейки; движение N:1
документ-основание; документ 1:N версии; согласование 1:N этапы и
решения.

Это логическая модель, не готовая физическая схема. Нормализация,
индексы, ограничения, миграции и стратегия хранения файлов проектируются
отдельно.

## 26. API и серверные операции

Контракты формализованы и документированы. Для каждого модуля: список,
карточка, создание, изменение черновика, бизнес-команды, история, связи,
поиск и экспорт при наличии прав.

Для переходов использовать команды с бизнес-смыслом: принять задачу,
отправить на проверку, согласовать заявку, провести приёмку,
зарезервировать и выдать материал. Клиент не должен присылать
произвольный статус в обход процесса.

Ошибки имеют стабильный код и понятное описание. Различать валидацию,
отсутствие прав, отсутствие записи, конфликт версии, бизнес-конфликт,
недостаточный остаток, недопустимый переход и техническую ошибку.

Критичные команды должны быть идемпотентны или защищены от повторного
выполнения. При конкурентном редактировании возвращать конфликт, а не
молча затирать изменения.

## 27. PostgreSQL и jOOQ

Критичные ограничения обеспечивать на уровне БД, где возможно:
уникальность, обязательность, внешние ключи и допустимые диапазоны.
Многострочные бизнес-операции выполнять транзакционно.

Складская модель должна иметь проверяемый журнал движений. Актуальные
остатки могут поддерживаться отдельным механизмом, но должны сверяться с
журналом. Миграции схемы --- версионируемые и воспроизводимые. jOOQ
использовать для типобезопасных запросов в рамках его возможностей.

Не допускать N+1 запросов в списках и карточках. Для крупных выборок
определить индексы и проверить планы выполнения. Каскадное удаление
проведённых бизнес-данных запрещено.

## 28. Сквозные бизнес-сценарии

### 28.1. Потребность проекта

Руководитель создаёт проект, добавляет изделие и версию BOM, задаёт
количество, запускает расчёт. Система показывает потребность, остатки,
резервы и дефицит. Руководитель подтверждает план обеспечения. Для
дефицита создаются связанные закупочные потребности.

### 28.2. Закупка

Снабженец получает заявку, проверяет склад и аналоги, запрашивает
предложения, вносит цены и сроки, формирует сравнение, отправляет выбор
на согласование, создаёт заказ поставщику. Система отслеживает срок и
сообщает о задержке.

### 28.3. Приёмка

Кладовщик открывает ожидаемую поставку, сверяет позиции, фиксирует
количество, партии, серии и расхождения, выполняет контроль качества,
размещает материал и проводит документ. Остатки и обеспеченность проекта
обновляются, участники получают уведомление.

### 28.4. Выдача

Руководитель создаёт требование. Система проверяет остатки и
резервирует. Кладовщик комплектует по ячейкам, подтверждает количество,
передаёт получателю. Получатель подтверждает, расход проводится, проект
обновляет обеспеченность.

### 28.5. Чат задачи

Руководитель создаёт задачу и назначает исполнителя. У задачи доступно
обсуждение. Исполнитель принимает задачу, участники переписываются,
@упоминание создаёт уведомление. Статус отражается системным событием.
Исполнитель прикладывает результат и отправляет на проверку. Проверяющий
принимает или возвращает с комментарием.

### 28.6. Изменение BOM

Конструктор создаёт ревизию, система показывает отличия, версия
отправляется на согласование. После утверждения определяется
применяемость к активным проектам. Руководители принимают решение по
каждому проекту. Старые версии сохраняются.

### 28.7. Инвентаризация

Создаётся задание и учётный срез, назначается комиссия, вводится факт,
спорные позиции пересчитываются, формируются расхождения, согласуется
корректировка и создаются движения. История исходных данных сохраняется.

### 28.8. Возврат

Сотрудник оформляет возврат со ссылкой на выдачу. Кладовщик принимает в
отдельную зону, проверяет состояние и направляет в доступный остаток,
карантин или брак. Фактический расход проекта пересчитывается по
правилам.

### 28.9. Несоответствие

При приёмке обнаружен дефект. Создаётся несоответствие, партия
блокируется, снабженец получает уведомление, оформляется претензия,
назначается анализ и корректирующие действия. Закрытие --- после
подтверждения результата.

### 28.10. Контроль руководителя

Руководитель видит просрочки задач и поставок, фильтрует по проекту,
изучает историю сроков и обсуждение, создаёт корректирующую задачу и
назначает ответственного.

## 29. Обязательные системные инварианты

1.  Нельзя провести расход сверх доступного количества без утверждённого
    исключения.
2.  Нельзя провести один документ дважды.
3.  Проведённая операция исправляется корректировкой, а не удалением.
4.  Карантин и брак недоступны для обычной выдачи.
5.  Одно количество нельзя зарезервировать дважды.
6.  Нельзя закрыть задачу без обязательной приёмки.
7.  Нельзя утвердить документ без обязательных согласований.
8.  Утверждённая BOM не меняется незаметно.
9.  Удаление пользователя не уничтожает его историю.
10. Закрытый чат и его файлы защищены проверкой прав.
11. Существенное изменение во время согласования требует
    предусмотренного перезапуска.
12. Проект нельзя закрыть с обязательными незавершёнными процессами без
    исключения.
13. Архивную номенклатуру нельзя использовать без разрешённого сценария.
14. Серийный номер уникален.
15. Закупочная потребность связана с заказом, поставкой и приёмкой.
16. Изменения ответственного, срока и статуса отражаются в истории.
17. Сервер проверяет права независимо от UI.
18. Повторная команда не приводит к двойному проведению.
19. Конкурентное изменение обнаруживается.
20. Количества рассчитываются с корректной точностью единиц.

## F.1. Разделение коммуникаций

- **Chat** — общие личные и групповые чаты сотрудников. Общий чат не является списком задач.
- **Task Chat** — обсуждение внутри конкретной задачи, связанное с её историей. Сообщения сохраняются в истории задачи; у каждого видны автор и время отправки. Системные события отличаются от сообщений пользователей.
- **Mail** — встроенный клиент общих почтовых ящиков подразделений через IMAP/SMTP. Почта не является каналом Task Chat.

## F.2. Доступ к Task Chat

Исполнитель, соисполнители, наблюдатели, инициатор и проверяющий задачи автоматически получают доступ к её обсуждению. Для задачи подразделения просмотр задачи и обсуждения доступен всем сотрудникам подразделения; право просмотра не означает права редактирования или выполнения. Добавление участника открывает ему всю историю; удаление прекращает доступ, только если не осталось другого основания доступа. Сервер проверяет актуальные основания при чтении, отправке сообщения, скачивании вложения и прямом переходе по ссылке. Отдельного ручного списка участников Task Chat нет.

## F.3. Граница Mail

Подключаются **только общие ящики подразделений**; личные почтовые аккаунты сотрудников вне объёма. Сотрудники с разрешением работают с входящими, отправленными, черновиками, папками и вложениями нескольких общих ящиков, отвечают и пересылают письма. Доступ разграничивается по ящику и действию.

IMAP служит для чтения и синхронизации, SMTP — для отправки. ERP не ведёт независимый архив писем: почтовый сервер остаётся источником содержимого, папок и флагов. Допустимы только необходимые служебные данные синхронизации и аудита; хранение полного содержимого и вложений как самостоятельной копии не требуется.

**Не входят в объём Mail:** привязка письма к проекту или задаче, создание задачи из письма, перенос вложений в Documents и специальные связи почты с закупками либо иными бизнес-процессами. Эти действия нельзя считать обязательными на основании общих требований к сквозным связям.

## F.4. Очерёдность

Mail реализуется после базовых пользователей и прав, проектов, задач, общего Chat и Task Chat. Его отсутствие не блокирует проверку первых сквозных сценариев задач и проектов. Правила доступа к общему ящику, синхронизация и отправка проверяются отдельно перед приёмкой Mail.

## F.5. Уточнения по задачам

Задача может быть проектной, личным поручением или задачей подразделения. Сотрудник может создать поручение себе; руководитель или уполномоченный сотрудник — другому. Для задачи подразделения можно назначить исполнителя из другого подразделения при наличии полномочий.

После закрытия задача и Task Chat доступны только для чтения: отправка сообщений, добавление файлов и изменение состава участников запрещены. Для продолжения работы уполномоченный пользователь повторно открывает задачу с указанием причины. Это правило **заменяет ранее обсуждавшуюся возможность писать в закрытую задачу**.

Отдельный проверяющий не обязателен для каждой задачи. Обязательность приёмки определяется типом работы; исполнитель не закрывает самостоятельно задачу, требующую приёмки. Матрица типов и ответственных за проверку утверждается отдельно.

## F.6. Задел ведущего инженера

Задел — общий запас материалов предприятия для будущих проектов на складе, а не личный остаток инженера и не изготовленные заранее изделия. Ведущие инженеры планируют перечни по направлениям; закупка требует согласования уполномоченного руководителя. При появлении проекта согласованное количество выделяется из задела и резервируется под проект. Резерв не является физической выдачей. История хранит исходный задел, проект, решение и согласование, номенклатуру, количество, время и остаток задела.

# Приложение G. Уточнения первой версии и первого релиза

**Дата фиксации:** 13.11.2026. Уточнения ниже имеют приоритет при определении объёма первой версии. Предложения, явно помеченные как рекомендации, требуют отдельного утверждения.

## G.1. Размещение, вход и масштаб

Первая версия размещается на собственном сервере предприятия в локальной инфраструктуре (`192.168.1.200`). Доступ сотрудников из интернета пока не утверждён и не является условием первого релиза. Вход — по локальным учётным записям ERP с логином и паролем; пользователи, роли и права хранятся в ERP. LDAP/Active Directory на старте не подключается. Ориентир — около 70 сотрудников и 5–10 подразделений; одновременная нагрузка измеряется и проверяется отдельно.

## G.2. Проектные задачи и коммуникации

Каждый участник проекта может просматривать все задачи проекта, их статусы, прогресс и обсуждения. Право просмотра не означает право изменять задачу или выполнять её действия. Это дополнительное основание доступа к Task Chat, наряду с основаниями в приложении F. Всякий отзыв доступа проверяет оставшиеся основания.

Сообщения Chat и Task Chat доставляются без обновления страницы. История хранится на сервере; после переподключения клиент получает пропущенные сообщения. Нужны центр уведомлений внутри ERP и браузерные уведомления. WebSocket — рекомендуемая технология, а не отдельно утверждённый протокол.

## G.3. Клиенты и UI

Основной интерфейс — настольный браузер. На телефоне обязательны уведомления, чаты, просмотр задач, комментарии, согласование и приёмка. Для устройств кладовщиков обязательны быстрый поиск номенклатуры, приёмка, перемещения, выдача и инвентаризация. Интерфейс адаптивен. Визуальный ориентир — фирменная айдентика [avem.ru](https://avem.ru); конкретные компоненты и макеты утверждаются отдельно.

## G.4. Начальные данные и состав первой поставки

ERP стартует с чистой базой. Данные и история 1С и Битрикс не мигрируются. Пользователи, подразделения, номенклатура, склады, проекты, задачи и документы создаются заново. Начальные остатки вводятся вручную после фактической инвентаризации. Требование раздела 20 об импорте не означает обязательную миграцию старых систем для первой версии.

Подтверждён первый сквозной результат: проект → задача → назначение → Task Chat → уведомление → выполнение → приёмка. Для него сначала нужна минимальная карточка проекта с участниками и правами; расширенные функции проекта могут следовать позже. Решением MVP-01 в первую рабочую поставку включён только Task Chat; общий Chat перенесён на следующий этап. Инфраструктура сообщений должна допускать его последующее добавление без переделки Task Chat. Остальная точная граница первой поставки согласуется отдельно.

# Приложение H. Будущее Android-приложение склада

**Статус:** следующий этап после полноценной серверной логики WMS и API; отдельный Android-клиент пока не входит в текущую реализацию.

## H.1. Сценарии

Android-приложение для кладовщиков и других работников, выполняющих операции с материалами, должно поддерживать сканирование и поиск номенклатуры по штрихкоду, приёмку, выдачу, перемещение между складами и местами хранения, инвентаризацию, просмотр остатков, резервирование и комплектацию заказов.

## H.2. Требования к серверной архитектуре уже сейчас

1. Позиция номенклатуры может иметь несколько штрихкодов. Каждый штрихкод однозначно определяет номенклатуру и, когда нужно, упаковку или единицу учёта.
2. Операции WMS выполняются через API ERP. Мобильный клиент не подключается к PostgreSQL напрямую и не определяет окончательный результат учётной операции локально.
3. API поддерживает авторизацию мобильного клиента. Сервер проверяет права, ограничения и переходы, включая проведение документа, резерв и доступный остаток.
4. Ввод штрихкода отделён от бизнес-операции: Android-клиент должен принимать данные встроенного или Bluetooth-сканера, в том числе сканера, работающего как клавиатура.
5. Контракты WMS не должны зависеть от Compose/Web и должны быть пригодны для использования веб-клиентом и будущим Android-клиентом.

Технологический вариант клиента — Kotlin и Jetpack Compose для Android в рамках существующего Kotlin-стека. Его точная конфигурация и устройства уточняются перед этапом реализации. Сначала строятся и проверяются серверные операции WMS и API; новый клиент подключается к ним без переписывания учётных правил.

Для отдельных категорий правила контроля качества могут быть определены позже. Это уточняет общий сценарий разделов 8.4–8.5.

# Приложение J. Утверждённая целевая модель производственного процесса

**Статус:** все девять пунктов утверждены ответом раунда 4 как целевая модель ERP. Это не означает включение всех функций в первый релиз. Существующие требования разделов 5, 10, 12, 15, 16 и 25 сохраняются; уточнения ниже имеют приоритет при детализации процесса. Полномочия конкретных должностей и примеры реальных проектов ещё требуется согласовать.

1. **Типы проектов:** разработка под заказ, повторное изготовление, модернизация, ремонт, внутренний проект. В первой очереди — все, кроме ремонта. Тип проекта не ограничивает использование общих задач, документов, BOM, потребностей и WMS.
2. **Открытие проекта:** решение уполномоченного руководителя с сохранением основания, инициатора, руководителя проекта, даты и истории. Возможные основания: договор, ТЗ, повторный заказ, внутренняя разработка, заявка на модернизацию. Договор не обязателен для каждого проекта.
3. **Потребность:** отдельная центральная сущность с номером и историей, допускающая частичное покрытие несколькими поставками и закупку, покрывающую несколько потребностей. Список оснований и правила согласования ещё уточняются.
4. **Ревизия BOM в заказе:** производственный заказ фиксирует утверждённую ревизию. Новая ревизия не меняет начатый заказ автоматически; изменение требует решения с анализом последствий и сохранением прежней версии.
5. **Испытания первой очереди:** протокол в Documents, связь с проектом и производственным заказом, дата, исполнитель, результат годно/не годно, замечания и решение о повторе. Хранение отдельных измерений и автоматическое формирование протоколов относятся к более позднему этапу.
6. **Инженерное изменение:** формальный запрос с причиной, технической оценкой, анализом уже заказанных материалов и выполненных работ, влиянием на сроки и решением уполномоченного руководителя. Утверждение фиксирует, с какой ревизией продолжается заказ; уже проведённые операции не переписываются.
7. **Поздние этапы:** отгрузка, монтаж и пусконаладка — после первой очереди; гарантия, ремонты и сервисная история — ещё позже. Уже в первой очереди хранится связь экземпляра изделия с заказчиком, проектом, серийным номером и комплектом документов.
8. **WMS до Android:** адаптивный веб-интерфейс на ПК, планшете, телефоне и устройствах со сканером; основные операции доступны через существующий серверный WMS API. Отдельное Android-приложение подключается позже.
9. **Готовое изделие:** отдельная карточка экземпляра с моделью, серийным номером, проектом, производственным заказом, ревизией BOM, датой изготовления, испытаниями, документацией, заказчиком и будущей историей обслуживания. Это расширяет уже предусмотренный в разделе 15 серийный учёт; не создаёт дубликат карточки типового изделия из НСИ.

# Приложение K. Связи изделия, выпуск и техническая приёмка

**Статус:** утверждённые уточнения раунда 4. Они конкретизируют приложение J; поля и полномочия, явно отмеченные как открытые, утверждаются отдельно.

## K.1. Модель, ревизия, экземпляр

Один проект может содержать несколько разных моделей изделий и несколько производственных заказов. Одна модель может применяться в нескольких проектах и повторно производиться без создания новой модели. У модели могут быть разные ревизии BOM. Следует различать типовое **изделие/модель**, утверждённую **ревизию состава и документации** и физический **экземпляр с серийным номером**.

Производственный заказ поддерживает единичный и партийный выпуск. Он хранит плановое и фактическое количество, модель, закреплённую ревизию BOM, этапы, исполнителей, материалы, сроки и результаты контроля. При фактическом завершении изготовления каждого экземпляра создаётся отдельная карточка и присваивается уникальный серийный номер. Заказ на десять единиц образует десять карточек. Создание заказа само по себе не создаёт готовых экземпляров.

## K.2. Последствия инженерного изменения

Изменение схемы или BOM не списывает, не возвращает и не заменяет материалы автоматически. Инженер создаёт запрос; конструктор или ведущий инженер оценивает компоненты, снабжение — уже заказанные и оплаченные материалы, склад — фактическое наличие, производство — выданные/установленные компоненты, руководитель проекта — совокупное влияние. Уполномоченное лицо утверждает решение для каждой затронутой позиции: оставить, вернуть поставщику или на склад, заменить, зарезервировать под другой проект, списать либо использовать с оформленным техническим отклонением. Причина, ответственный и согласующий сохраняются. Физически установленный компонент требует оценки переделки или разрешённого использования. Все складские действия проходят через WMS с историей.

## K.3. Испытания и запрет отгрузки

Исполнитель проводит испытания, прикладывает протокол, фиксирует результат и замечания. Уполномоченный технический приёмщик проверяет результаты и подтверждает «Годно» или «Не годно» под личной учётной записью ERP с записью в аудит. Конкретный носитель полномочия ещё не назначен; юридически значимая ЭП не обязательна в первой версии, её необходимость проверяется перед промышленным внедрением.

«Не годно» и незакрытые критические замечания блокируют отгрузку. Незначительное замечание допускается только с документированным разрешением на отклонение; если затронуты требования заказчика, учитывается его согласование. Исключение из обычного порядка имеет ответственного и обоснование. Закрытие производственного заказа само по себе не разрешает отгрузку.

## K.4. Фактическая конфигурация экземпляра

Хранится **фактическая конфигурация изготовленного экземпляра**: модель, ревизия BOM, серийный номер, фактически установленные компоненты и замены, утверждённые отклонения, применённые версии ПО и документов, испытания и комплект документации. Обязательность полей зависит от типа изделия и определяется утверждённым регламентом; подробности — в L.4.

# Приложение L. Утверждённые правила документов и согласований

**Статус:** все семь правил L.1–L.7 утверждены ответом пользователя как целевые требования. Реализация поэтапная: утверждение требования не включает все функции в первый релиз. Конкретные должности, критерии критичности и перечни обязательных документов утверждаются внутренними регламентами предприятия.

## L.1. Раздельные полномочия

Используются отдельные настраиваемые права `PROJECT_OPEN`, `PROJECT_CLOSE`, `BOM_APPROVE` и `ENGINEERING_CHANGE_APPROVE`. Один пользователь может иметь несколько прав; каждое действие пишет фактического исполнителя в аудит. При закрытии проекта система проверяет незавершённые производственные заказы, задачи, закупки и документы, не закрывая их автоматически. Должности и лица, получающие полномочия, ещё не определены.

## L.2. Персональное подтверждение технической приёмки

Для первой версии достаточно персонального подтверждения под учётной записью ERP; подтверждение от имени другого сотрудника запрещено. Аудит фиксирует автора, дату и время, объект, версию документа, принятое решение, протокол и историю решений, а также замечания и комментарий при наличии. Это подтверждение не считается автоматически юридически значимой электронной подписью. Интеграция с такой подписью не обязательна в первой версии; перед промышленным внедрением ответственные за качество и юридическое сопровождение проверяют нормативные и договорные требования.

## L.3. Критичность замечаний и разрешение отклонений

Различаются полномочия классифицировать замечание, принять техническое решение и разрешить отгрузку с незначительным отклонением (`SHIPMENT_DEVIATION_APPROVE`). Последнее требует оформленного разрешения. Если затронуты требования заказчика, согласие регистрируется **вручную**: скан письма, PDF или другой подтверждающий документ, дата, представитель заказчика при наличии, содержание отклонения, связь с конкретным экземпляром и разрешением на отгрузку, ответственный за регистрацию. Одной отметки без подтверждения недостаточно. Автоматическая интеграция с Mail не требуется.

Технический руководитель организует подготовку критериев вместе с ведущими инженерами и ответственным за качество, если такая функция выделена. Руководство предприятия утверждает критерии и перечень лиц с правом разрешать отгрузку с отклонением. В ERP полномочия назначаются правами, а не названием должности в коде. Конкретные критерии и сотрудники пока не определены.

## L.4. Независимые ревизии и конфигурация экземпляра

Независимо версионируются BOM, конструкторские документы и ПО. Для изготовленного экземпляра фиксируется фактическая конфигурация: модель и серийный номер, ревизия BOM, применённые версии документов и ПО (название, версия, сборка), установленные компоненты, согласованные замены и отклонения, испытания и комплект документов. Конфигурация отражает фактически изготовленное, а не только плановую BOM. Обязательность отдельных полей зависит от типа изделия и определяется его регламентом.

## L.5. Версии документов

Документ имеет постоянную карточку; версии внутри неё имеют номер, автора, дату, статус и историю согласования. Утверждённая версия неизменяема. Изменение создаёт новую версию в той же карточке; производственный заказ и экземпляр ссылаются на **конкретную версию**, а не только на карточку. При изменении фиксируется влияние на уже выпущенные экземпляры и решение по каждому затронутому экземпляру.

## L.6. Маршруты согласований

Используются типовые настраиваемые маршруты и ручное назначение согласующих без сложного BPM-конструктора. Маршрут состоит из этапов и одного либо нескольких согласующих на этапе; решение — утвердить, отклонить или вернуть — хранит автора и время. Выполненное решение не редактируется незаметно. Существенное изменение объекта требует новой версии/повторного согласования. Ручное изменение маршрута доступно по праву и аудируется. Шаблоны маршрутов для потребности, закупки, BOM, инженерного изменения, техприёмки и отклонения требуют отдельной матрицы. Изменение состава согласующих, маршрутов и полномочий не должно требовать правки исходного кода.

## L.7. Два контрольных списка

Отдельно проверяется **закрытие производственного заказа**: сам заказ, утверждённая ревизия BOM, фактическая комплектация, документы движений материалов при их наличии, сборочная документация по типу изделия, протоколы при обязательных испытаниях, решение техприёмки при её обязательности и карточки/серийные номера всех фактически изготовленных экземпляров.

Отдельно проверяется **отгрузка**: закрытый заказ, карточки экземпляров, утверждённые результаты обязательных испытаний и решения «Годно», отсутствие блокирующих замечаний, разрешения на отклонения и подтверждение заказчика при необходимости, паспорт/руководство по типу изделия и применимые отгрузочные документы. Проверяются статус, версия и связь документа с конкретным экземпляром, а не только наличие файла. Обязательность элементов настраивается по типу изделия и заказа; единый универсальный перечень файлов не используется.

Перечни готовят ведущие инженеры по направлениям вместе с техническим руководителем, привлекая конструкторов, программистов, сборщиков, электромонтажников, испытателей, снабжение и склад по своим документам. Итоговый перечень утверждает руководство предприятия. Конкретные матрицы ещё не составлены.

# Приложение M. Утверждённое поведение интерфейса UI/UX

**Дата фиксации:** 13.11.2026. Утверждены решения M.1–M.10. Они конкретизируют разделы 4 и 23 и определяют поведение интерфейса до разработки макетов. Это не утверждённая дизайн-система и не включение всех целевых функций в первую рабочую поставку.

## M.1. Главная страница

После входа открывается единая главная страница с персональным содержимым, а не отдельные интерфейсы для разных должностей. Состав определяется правами, участием в проектах и назначенными пользователю действиями; у сотрудника может быть несколько ролей.

Приоритет содержимого:

1. Просроченные задачи и объекты, требующие действия пользователя.
2. Задачи на сегодня и ближайшие сроки.
3. Согласования и приёмки.
4. Непрочитанные сообщения и упоминания.
5. Рабочие очереди подразделения.
6. Дополнительные показатели по правам.

Каждый показатель открывает список первичных записей. Пользователь может менять порядок необязательных блоков, но настройка не должна скрывать существование обязательной очереди действий. Показатели без определённой методики расчёта и фиктивные данные не отображаются.

## M.2. Левое меню и избранное

Используется единое левое меню с доступностью разделов по правам. Целевая структура навигации отделена от состава первой рабочей поставки.

Для первого сквозного результата основными разделами являются «Главная», «Мои задачи», «Проекты» и «Избранное». Отдельного раздела общего Chat в первой поставке нет по решению MVP-01; обсуждение открывается внутри задачи. «Снабжение», «Склад», «Номенклатура и BOM», «Производство» и самостоятельный раздел «Документы» появляются вместе с реальной функциональностью, а не как пустые экраны. В целевой структуре также предусматриваются «Согласования», «Контрагенты», «Отчёты» и «Администрирование» по правам и наличию функций.

Центр уведомлений открывается из верхней панели; обязательный дублирующий пункт в левом меню не требуется. Настройки доступны через профиль. Меню поддерживает сворачивание, заметный активный раздел и счётчики новых событий. Статус не обозначается только цветом.

Избранное персональное и позволяет закреплять разделы и конкретные записи. После отзыва доступа запись не показывается в избранном; прямой переход повторно проверяется сервером.

## M.3. Представления проектов и задач

| Представление | Решение |
| --- | --- |
| Таблица задач | Обязательна |
| Таблица проектов | Обязательна |
| Канбан задач | Входит в первую полноценную версию Task Manager, но не блокирует первый сквозной сценарий |
| Канбан проектов | Более поздний этап |
| Календарь | Более поздний этап |
| Диаграмма Ганта | После появления достоверных сроков и зависимостей |

Таблицы поддерживают серверную пагинацию, фильтры, сортировку, поиск, настройку колонок и сохранённые представления в соответствии с разделом 23.3. При возврате из карточки сохраняются состояние списка и положение, если это возможно.

Перетаскивание карточки канбана вызывает разрешённую бизнес-команду, а не произвольную запись статуса. Если переход требует причины или комментария, открывается соответствующая форма. Не требуется выводить каждый статус отдельной колонкой: доска может группировать статусы по настроенному процессу, а точный статус остаётся видимым в карточке.

## M.4. Карточка проекта

Первый экран проекта является обзорным. Он показывает номер и название, статус и текущий этап, руководителя и участников, плановые и фактические даты, ближайшую контрольную точку, просроченные и ближайшие задачи, блокировки и критические риски, требующиеся от пользователя действия и последние события. Основные действия зависят от прав.

Подробные данные размещаются во вкладках: «Обзор», «Этапы», «Задачи», «Изделия», «Потребности», «Документы», «Обсуждение» при наличии проектного чата и «История». В целевой структуре предусматриваются также «Риски» и «Изменения». Вкладки появляются по мере реализации соответствующих функций и с учётом прав.

Процент готовности отображается только при определённой методике расчёта; иначе показывается состояние этапов без необоснованного процента. Обсуждение проекта не заменяет обсуждения задач, а история изменений не смешивается с перепиской.

## M.5. Карточка задачи и обсуждение

На широком экране описание и обсуждение доступны одновременно: описание, ответственные, сроки, статус, файлы и связи располагаются слева, обсуждение — справа. На промежуточной ширине панель обсуждения может сворачиваться. На телефоне используются вкладки «Описание» и «Обсуждение» со счётчиком непрочитанного; черновик сообщения сохраняется при переключении.

Сообщения и системные события образуют общую хронологию. Системные события визуально отличаются, оформляются компактнее и содержат инициатора, время и понятное описание изменения. Предусматривается фильтр «Все / Сообщения / События», по умолчанию — «Все». Полная аудиторская история остаётся отдельной.

После закрытия задачи обсуждение доступно только для чтения. Поле ввода и добавление файлов недоступны; показывается режим «Только чтение» и действие «Открыть повторно» для уполномоченного пользователя с обязательным указанием причины.

## M.6. Согласование и приёмка на телефоне

Допускается решение после просмотра краткой сводки, если полный комплект материалов доступен и выполнены обязательные проверки. Принудительное открытие каждого документа не требуется и само по себе не доказывает ознакомление. Если обязательные исходные материалы отсутствуют или недоступны, техническое решение по одной сводке не разрешается.

Для технической приёмки показываются конкретный экземпляр и производственный заказ, ревизия, версия протокола, результат испытаний, критические и незначительные замечания, отклонения и разрешения, обязательные документы и признаки их отсутствия. Пользователь может открыть полные документы.

Решение привязывается к версии объекта и документов. При изменении версии до подтверждения сервер отклоняет устаревшую команду и требует повторной проверки. Возврат или отклонение требует комментария, если это предусмотрено процессом. Критичные решения не выполняются офлайн и не считаются завершёнными до успешного ответа сервера.

Приёмка задачи, техническая приёмка изделия и складская приёмка являются разными сценариями с разным контекстом, даже при использовании похожих компонентов интерфейса.

## M.7. Браузерные уведомления

По умолчанию браузерные уведомления нейтральные и не содержат текста сообщения, названия проекта или задачи. В режиме без предпросмотра эти сведения не включаются в данные push-сообщения; передаются только идентификатор события и допустимая нейтральная категория.

Переход по уведомлению открывает объект после входа и повторной проверки прав. Полное содержание доступно в центре уведомлений ERP по правам пользователя. Браузерное уведомление не является единственным каналом доставки: непрочитанные события сохраняются в центре. Персональная настройка предпросмотра текста может быть добавлена позже и по умолчанию выключена.

## M.8. Визуальные ориентиры

Подтверждённый фирменный ориентир — [avem.ru](https://avem.ru). Сторонние скриншоты интерфейсов являются только иллюстрациями компоновки, а не образцами дизайна ERP. Цвета и шрифты сайта не становятся утверждённой дизайн-системой автоматически.

ERP использует собственный набор компонентов для плотных таблиц, форм, статусов, рабочих очередей и мобильных действий. Интерфейс остаётся сдержанным, читаемым и адаптивным для настольных компьютеров, телефонов и складских устройств. Конкретные макеты и права использования фирменных ресурсов утверждаются отдельно.

## M.9. Глобальный поиск

Глобальный поиск постоянно доступен в верхней панели. Он ищет объекты, перечисленные в разделе 4.3, включая сообщения, по мере реализации соответствующих модулей. Результаты группируются по типам и ведут к первичным записям.

Поиск учитывает права на каждый объект и не раскрывает закрытые данные через названия, фрагменты текста или количество результатов. Нереализованные типы объектов не показываются как работающие категории поиска.

## M.10. Быстрые действия

Единое меню создания доступно из рабочих областей и показывает только реально реализованные и разрешённые действия. В первой поставке приоритетно создание задачи; проект доступен при соответствующем полномочии. Отдельного глобального действия создания сообщения без общего Chat нет: сообщение создаётся внутри доступного Task Chat. Потребность, документ и другие объекты добавляются вместе со своими модулями.

Быстрая форма содержит минимум обязательных полей и позволяет перейти к полной карточке. Создание черновика проекта само по себе не означает открытие проекта: открытие выполняется отдельным решением с правом `PROJECT_OPEN` и аудитом.

## Открытые детали после приложения M

Приложение не утверждает методику процента готовности и остальных показателей главной, конкретные матрицы обязательных материалов для видов согласования и приёмки, а также дополнительные внутренние интерфейсы или фирменные материалы как образцы. Эти детали определяются отдельно до соответствующих макетов и реализации.

# Приложение N. MVP-02 — минимальная карточка задачи

**Дата фиксации:** 13.11.2026. Состав полей, связей и перечисленные правила утверждены для первой рабочей поставки. Приложение не определяет набор статусов, допустимые переходы и полную матрицу полномочий; они согласуются отдельно. Исключения относятся только к первой поставке и не отменяют целевые функции раздела 6.

## N.1. Идентификация и область задачи

- Внутренний ID формируется сервером и не редактируется.
- Номер задачи генерируется автоматически и отображается пользователю.
- Область задачи обязательна и хранится явно: личная, проектная или подразделенческая.
- Проект обязателен только для проектной задачи.
- Подразделение обязательно только для подразделенческой задачи.
- Тип работы обязателен независимо от области задачи.
- Область задачи нельзя определять по наличию или отсутствию `project_id`.
- Связи с проектом и подразделением должны соответствовать выбранной области.

Область задачи определяет её связь и основания видимости, а тип работы — необходимость отдельной приёмки. Это разные атрибуты.

## N.2. Содержание и участники

Минимальная карточка содержит:

- название;
- описание;
- критерии приёмки;
- результат выполнения;
- инициатора;
- одного основного исполнителя;
- соисполнителей;
- наблюдателей;
- проверяющего.

Название обязательно. Описание обязательно при назначении задачи другому сотруднику; для личной задачи оно может быть пустым. Инициатор по умолчанию является текущим пользователем и не меняется произвольно. Для личной задачи основным исполнителем по умолчанию является сам сотрудник.

Основной исполнитель один и должен быть назначен до начала исполнения. Назначение задачи подразделению не отменяет необходимость ответственного владельца. Соисполнители и наблюдатели необязательны.

Критерии приёмки обязательны, если тип работы требует отдельной проверки. Проверяющий обязателен только для таких типов работ и должен отличаться от основного исполнителя.

## N.3. Сроки и рабочие данные

- Дата создания фиксируется автоматически.
- Плановое начало необязательно.
- Срок выполнения обязателен до передачи задачи в работу.
- Дата завершения фиксируется системой.
- Статус изменяется только разрешёнными бизнес-командами, а не произвольной записью поля.
- Приоритет обязателен; значение по умолчанию — «Обычный».
- Причина блокировки и ответственный за снятие блокировки обязательны при блокировке.
- Автор и время блокировки фиксируются автоматически.

## N.4. Результат, вложения и аудит

- Результат выполнения может содержать текст и/или вложения.
- Результат обязателен при отправке задачи на проверку.
- Вложения имеют автора, дату добавления и отдельную серверную проверку доступа.
- История изменений хранится отдельно от редактируемых полей.
- Версия записи используется для обнаружения конкурентного редактирования.
- Task Chat и полная история являются связанными разделами карточки, а не её редактируемыми полями.

## N.5. Дополнительные обязательные правила

1. Причины возврата, отмены и повторного открытия фиксируются отдельными событиями с автором и временем.
2. Обязательность полей проверяется сервером при выполнении соответствующей команды, а не только в форме.
3. Изменение исполнителя, срока и других значимых данных сохраняется в истории.
4. Доступ к просмотру задачи не означает автоматического права редактировать её или выполнять действия.
5. Удаление и изменение вложений не должны обходить аудит и правила доступа. После закрытия задачи также действуют правила только для чтения из приложения F.

## N.6. Исключено из первой поставки

В минимальную карточку и первую рабочую поставку не входят:

- родительские задачи и подзадачи;
- этап проекта;
- зависимости между задачами;
- чек-листы;
- теги;
- оценка трудоёмкости;
- учёт фактического времени;
- повторение и шаблоны задач.

Это ограничение первой поставки, а не окончательный отказ от перечисленных функций в целевой системе.

## N.7. Открытые детали

Для последующей детализации отдельно определяются:

- справочник типов работ и признаки необходимости приёмки;
- допустимые значения приоритета;
- формат автоматического номера задачи;
- допустимые форматы и ограничения файлов;
- правила назначения проверяющего;
- статусы задач, допустимые переходы и матрица полномочий.
