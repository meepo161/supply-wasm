# Журнал проектных решений

Здесь фиксируются решения, прямо подтверждённые пользователем в обсуждении. Это источник актуальных уточнений к [ТЗ](ТЗ_ERP_WMS_CHAT_TASK_MANAGER.md) и [целевой архитектуре](target-architecture.md). Предложения ниже не считаются утверждёнными. Статус реализации каждого пункта — **не реализовано**, пока он не подтверждён кодом и проверками.

## Принято

| ID | Область | Решение |
| --- | --- | --- |
| D-01 | Стек | Сервер Kotlin/Ktor, клиент Kotlin/Wasm/Compose, PostgreSQL и jOOQ — из ТЗ. Для внедрения зависимостей используем Koin. |
| D-02 | Архитектура | Один модульный монолит с общими пользователями и справочниками; Chat, Task Chat и Mail выполняют разные задачи. |
| D-03 | Task Chat | Исполнитель, соисполнители, наблюдатели, инициатор и проверяющий видят обсуждение. Для задачи подразделения просмотр доступен всем её сотрудникам; для проектной — всем участникам проекта. Добавление участника открывает историю; удаление прекращает доступ, только если нет другого основания. Автор и время сообщения видны. |
| D-04 | Завершение задачи | **Последнее уточнение заменяет прежнее правило:** после закрытия задача и чат доступны только для чтения; новые сообщения, файлы и изменение участников запрещены. Возобновление работы требует повторного открытия уполномоченным пользователем с причиной. |
| D-05 | Область задачи | Задача может быть проектной, личным поручением или задачей подразделения. Связь с проектом не обязательна. |
| D-06 | Mail: ящики | Только общие почтовые ящики подразделений; несколько ящиков, доступ сотрудников разграничен. Личные аккаунты сотрудников не входят в объём. |
| D-07 | Mail: функции | Встроенный клиент через IMAP/SMTP: входящие, отправленные, черновики, папки, вложения, ответы и пересылка. Независимый архив писем в ERP не нужен. |
| D-08 | Mail: граница | Не нужны привязка писем к задачам/проектам, создание задач из писем или перенос вложений в Documents. |
| D-09 | Mail: очерёдность | Mail реализуется после базовых пользователей, прав, проектов, задач и чатов. |
| D-10 | Первый результат | Первый проверяемый сквозной сценарий: проект → задача → назначение → Task Chat → уведомление → проверка результата. Личное поручение и задача подразделения также должны поддерживаться задачами. |
| D-11 | Снабжение: основания | Потребность в материалах может возникать для проекта или для задела ведущего инженера. «Задел» означает **запас материалов для будущих проектов**, а не заранее изготовленные изделия/узлы. |
| D-12 | Личное поручение | Сотрудник может создать задачу себе; руководитель или уполномоченный сотрудник — другому. Видят инициатор, исполнитель, соисполнители, наблюдатели и руководитель с соответствующим правом; остальные не получают доступ автоматически. |
| D-13 | Задача подразделения | Все сотрудники подразделения видят задачу и обсуждение, но просмотр не даёт права редактировать или выполнять. Исполнителя из другого подразделения можно назначить при наличии полномочия. Руководитель подразделения контролирует назначение. |
| D-14 | Приёмка задачи | Проверяющий не обязателен для каждой задачи. Требование отдельной приёмки определяется типом задачи; исполнитель не закрывает самостоятельно задачу с обязательной приёмкой. Конкретная матрица типов и проверяющих требует настройки. |
| D-15 | Задел материалов | Физически это общий запас предприятия на складе. Ответственные ведущие инженеры планируют перечни по направлениям; закупка задела проходит согласование и утверждение уполномоченным руководителем. Личный остаток инженера не создаётся. |
| D-16 | Выделение задела проекту | При появлении проекта материалы из задела резервируются под проект после согласования; резерв не является физической выдачей. История фиксирует исходный задел, проект, решение и согласующего, номенклатуру, количество, время и оставшийся объём задела. |
| D-17 | Масштаб первой версии | Одно юридическое лицо — ООО «Авиаагрегат-Н»; полноценная мультитенантность сейчас не нужна. Внешние учётные записи поставщиков, подрядчиков и заказчиков в первую версию не входят. |
| D-18 | WMS и бухгалтерия | WMS ведёт оперативный и управленческий учёт материалов. Бухгалтерские проводки внутри ERP для первой версии не требуются; способ передачи данных бухгалтерии ещё не утверждён. |
| D-19 | Размещение | Первая версия размещается на собственном сервере предприятия в локальной инфраструктуре (`192.168.1.200`). SSH-доступ сейчас есть. Доступ сотрудников через интернет не утверждён и не обязателен для первого релиза. |
| D-20 | Вход | На старте локальные учётные записи ERP: логин/пароль, пользователи, роли и права в ERP. LDAP/Active Directory в первую версию не входит; возможность будущей интеграции учитывается при проектировании границы идентификации. |
| D-21 | Начальный масштаб | Ориентир — около 70 сотрудников и 5–10 подразделений. Число одновременных пользователей не задано; нагрузка проверяется тестом. |
| D-22 | Проектные задачи | Любой участник проекта видит все задачи и обсуждения проекта, их статусы и прогресс. Право просмотра само по себе не даёт права редактировать задачу или участвовать в её выполнении. |
| D-23 | Уведомления и сообщения | Нужны центр уведомлений в ERP и браузерные уведомления. Сообщения чатов доставляются без обновления страницы; история хранится на сервере и после переподключения клиент получает пропущенное. Конкретный транспорт ещё не утверждён. |
| D-24 | UI и устройства | Основной интерфейс — настольный браузер; визуальный ориентир — фирменная айдентика [avem.ru](https://avem.ru). Телефон: уведомления, чаты, просмотр задач, комментарии, согласование и приёмка. Складские устройства: быстрый поиск, приёмка, перемещения, выдача и инвентаризация. Интерфейс адаптивный. |
| D-25 | Начальные данные | Новая ERP стартует с чистой базы. 1С и Битрикс не мигрируются; пользователи, оргструктура, номенклатура, склады, проекты, задачи и документы заводятся заново. Начальные остатки вводятся вручную после фактической инвентаризации. |
| D-26 | Будущий Android-клиент | После серверной WMS планируется отдельное Android-приложение склада. Сканирование, поиск, приёмка, выдача, перемещения, инвентаризация, остатки, резервы и комплектация используют авторизованный WMS API; прямого доступа к PostgreSQL нет. Номенклатура имеет несколько однозначно разрешаемых штрихкодов, включая упаковку/единицу. Сканеры могут работать как клавиатура. Kotlin + Jetpack Compose — технологический вариант, конфигурация ещё не утверждена. |
| D-27 | Инициатива задела | Любой сотрудник может предложить позицию задела; ведущий инженер формирует и обосновывает план. Это не даёт права самостоятельно закупать или распоряжаться запасом; закупка и выделение проекту проходят полномочия и сохраняются в истории. В приложенном ответе это описано как ранее принятое решение. |
| D-28 | Выбор поставщика | Инициатор потребности выбирает предпочтительное предложение; уполномоченный снабженец оформляет заказ после согласования по порогам. Суммы и согласующие пока открыты. В приложенном ответе пороги названы ранее принятым решением. |
| D-29 | Приёмка без обязательного ОТК | На первом этапе кладовщик сверяет номенклатуру и количество и проводит документ; остаток обновляется после проведения. Обязательный контроль ОТК для каждой приёмки не нужен; правила контроля отдельных категорий добавляются отдельно. |
| D-30 | Резервы | Резерв допустим под проект, производственный заказ, задел, ремонт, задачу подразделения и другие основания. Резерв не является выдачей, уменьшает доступное количество, не может превышать его; создание, изменение и снятие имеют историю. В приложенном ответе это названо ранее принятым решением. |
| D-31 | Целевая производственная модель | Утверждены все девять пунктов приложения J к ТЗ как целевая модель. Это не означает, что все функции входят в первый релиз: типы проектов, открытие решением руководителя, центральная Потребность, ревизия BOM в заказе, базовый результат испытаний, процесс инженерных изменений, поздние пусконаладка/сервис, веб-WMS до Android и карточка изготовленного экземпляра. |
| D-32 | Связи проекта и изделия | Проект может содержать несколько моделей изделий и производственных заказов; модель применяется в разных проектах и имеет разные ревизии. Модель, ревизия и физический экземпляр — разные сущности. Повторное производство модели не создаёт новую модель. |
| D-33 | Выпуск заказа | Производственный заказ допускает единичный и партийный выпуск, хранит плановое и фактическое количество, модель, ревизию BOM, этапы, материалы, исполнителей, сроки и контроль. Карточка каждого экземпляра создаётся при фактическом завершении его изготовления; каждый получает уникальный серийный номер. |
| D-34 | Влияние инженерного изменения | Изменение не списывает и не заменяет материалы автоматически. Инженер, снабжение, склад, производство и руководитель проекта оценивают влияние; уполномоченное лицо утверждает судьбу каждой затронутой позиции. Возврат, замена, новый резерв, списание и отклонение оформляются соответствующими операциями WMS с историей. |
| D-35 | Испытания и отгрузка | Исполнитель фиксирует испытание, протокол и замечания; уполномоченный технический приёмщик подтверждает «годно/не годно» под личной учётной записью ERP с аудитом. «Не годно» и незакрытые критические замечания блокируют отгрузку; незначительные требуют разрешения на отклонение, а затрагивающие требования заказчика — подтверждённого согласия. Закрытие производственного заказа само по себе не разрешает отгрузку. Юридически значимая ЭП не входит в обязательный объём первой версии, но её необходимость проверяется до промышленного внедрения. |
| D-36 | L.1 — полномочия | Отдельные настраиваемые права `PROJECT_OPEN`, `PROJECT_CLOSE`, `BOM_APPROVE`, `ENGINEERING_CHANGE_APPROVE`; фактический исполнитель аудируется. Закрытие проекта проверяет связанные незавершённые процессы, не закрывая их автоматически. |
| D-37 | L.2 — техническое подтверждение | Персональная учётная запись, запрет действия от чужого имени, аудит автора, времени, объекта, версии и решения. Юридически значимая ЭП не обязательна в первой версии; требования к ней проверяют качество и юристы перед промышленным запуском. |
| D-38 | L.3 — замечания и отклонения | Классификация, техническое решение и разрешение отгрузки — разные полномочия; последнее через `SHIPMENT_DEVIATION_APPROVE`. Критерии готовят технический руководитель и ведущие инженеры с качеством при наличии, утверждает руководство. Согласие заказчика прикладывается вручную к конкретному изделию и разрешению; интеграции с Mail нет. |
| D-39 | L.4 — ревизии и конфигурация | BOM, КД и ПО версионируются независимо; карточка экземпляра фиксирует фактически применённые версии, компоненты, замены, отклонения, испытания и документы. Обязательность конкретных полей настраивается по типу изделия. |
| D-40 | L.5 — версии документов | Постоянная карточка содержит неизменяемые после утверждения версии. Производственный заказ и экземпляр ссылаются на конкретные версии; новая версия сохраняет историю и оценку влияния на уже изготовленные экземпляры. |
| D-41 | L.6 — согласования | Типовые настраиваемые маршруты и ручное назначение согласующих; решения и изменения маршрута аудируются. Изменение согласующих, полномочий и маршрутов не требует правки исходного кода. |
| D-42 | L.7 — контрольные списки | Отдельные настраиваемые проверки закрытия заказа и отгрузки, зависящие от типа изделия/заказа. Проверяются статус, версия и связь подтверждений, а не только файлы. Перечни готовят ведущие инженеры и технический руководитель с профильными участниками, утверждает руководство. |
| D-43 | UI/UX: приложение M | Утверждены M.1–M.10: единая персональная главная; меню по правам и реальной готовности модулей; таблицы и очерёдность представлений; обзор проекта и вкладки; двухпанельная задача на широком экране; мобильные решения с доступом к полным материалам и проверкой версий; нейтральные браузерные уведомления; avem.ru только как фирменный ориентир; глобальный поиск и быстрые действия с учётом прав. Подробности — в [приложении M к ТЗ](ТЗ_ERP_WMS_CHAT_TASK_MANAGER.md). |
| MVP-01 | Общий Chat | В первую рабочую поставку входит только Task Chat. Общий Chat между сотрудниками не входит и переносится на следующий этап. Инфраструктура сообщений должна допускать его последующее добавление без переделки Task Chat. Ранее утверждённые правила видимости, авторства и истории Task Chat сохраняются. Остальной предложенный состав MVP и исключения этим решением не утверждаются. |
| MVP-02 | Минимальная карточка задачи | Утверждены состав полей и связей, явная область задачи, обязательный тип работы, участники, сроки, результат, вложения, аудит и серверные проверки. Из первой поставки исключены подзадачи, этап проекта, зависимости, чек-листы, теги, трудоёмкость, фактическое время, повторение и шаблоны. Это ограничение первой поставки, не отказ от целевых функций. Подробности — в [приложении N к ТЗ](ТЗ_ERP_WMS_CHAT_TASK_MANAGER.md). Статусы, переходы и полная матрица прав отдельно не утверждены. |
| D-44 | Начало реализации | Пользователь повторно и явно поручил начать полную реализацию после предупреждения об открытых SPEC/TECH. Разрешено использовать подготовленные проекты SPEC-001–SPEC-003 и рекомендации TECH-001 как рабочую базу разработки. Это разрешение не утверждает автоматически открытые бизнес-правила; последующие уточнения пользователя остаются обязательными и требуют синхронизации кода и документации. |
| D-45 | Таблицы UI | Для таблиц проектов, задач и других рабочих списков использовать [unchil/ComposeDataGrid](https://github.com/unchil/ComposeDataGrid) версии `0.2.10-1`. Библиотека подключена как Git submodule `vendor/ComposeDataGrid` с Gradle composite build и координатами `com.github.unchil:un7datagrid:0.2.10-1`, без токена GitHub Packages. `TasksTable` использует `Un7KCMPDataGrid`; сборка Wasm и рендер в браузере проверены. |
| D-47 | Визуальный стиль UI | По поручению пользователя от 14.11.2026 интерфейс оформлен собственной дизайн-системой: акцентный синий `#1668E3` с градиентами «синий → индиго → фиолетовый» и циановыми/бирюзовыми акцентами, светлая и тёмная темы, градиентный сайдбар с группами меню, стеклянные карточки, собственный набор векторных иконок и мягкие скругления. Токены и компоненты находятся в `app/shared/src/commonMain/kotlin/org/example/project/ui/theme/`. Это оформление не заменяет утверждённую дизайн-систему: макеты и права на фирменные ассеты по-прежнему требуют отдельного решения. |
| D-46 | Адреса разработки | Backend/API всегда запускается на `http://localhost:8080`, frontend/Wasm — на `http://localhost:8081`. Клиент обращается к API только на `8080`; пользователь открывает страницу на `8081`. Порты нельзя менять местами. |
| D-48 | Заказ поставщику и частичные поставки (SUP-15, SUP-16) | Заказ создаётся только из предложения в статусе `SELECTED` и только у проверенного поставщика; `offer_id` уникален — одно предложение даёт ровно один заказ, обойти выбор инициатора нельзя (следует из D-28). Количество в заказе только уменьшается относительно предложения. Отправка поставщику требует согласования (`approved_at`), свой заказ согласуется только с правом `suppliers:approve_order_any`. Существенные изменения (количество, срок поставки, условия оплаты, адрес доставки) требуют обоснования и при статусе ≠ `DRAFT` возвращают заказ в `PENDING_APPROVAL`. Поставки частичные, остаток и суммы считает база; связь заказа с потребностями — многие-ко-многим. Оплата, счета-фактуры и претензии вне объёма; суммовые пороги и маршруты согласующих (§9.7) остаются открытым вопросом и не выдумываются. Приёмка WMS связана с заказом и поставкой — см. D-49. |
| D-49 | Приёмка по основаниям (WMS-PROC-001, SUP-16) | Приёмка всегда имеет основание: заказ поставщику, счёт, накладная/УПД, возврат, перемещение, начальный остаток или прочий документ. Для заказа, счёта, накладной, возврата и перемещения номер документа-основания обязателен; ссылаться на заказ можно только этим трём видам. Один документ-основание даёт ровно одну приёмку — уникальный индекс по (вид, номер документа), отменённый документ (`CANCELLED`) в проверку не входит; повторное проведение и перезапись проведённой приёмки отклоняются. Приёмка по заказу может быть частичной и многократной, но не может превышать заказанное: ожидаемое количество не вводится клиентом, оно считается из остатка заказа и уже принятого (проверяется дважды — при создании и при проведении, потому что между ними могла пройти другая приёмка). Расхождения «ожидалось / принято» фиксируются по строке как `SHORTAGE`/`SURPLUS` с обязательным обоснованием; без обоснования документ не создаётся. Остаток появляется только после успешного проведения в одной транзакции; проведённый документ неизменяем (триггер `wms_guard_receipt_mutation`), движение и остаток не дублируются. Заказ, накладная или счёт, появившиеся позже, связываются с уже проведённой приёмкой через append-only журнал `receipt_links`: остаток не пересоздаётся, повторная привязка тех же документов и конфликт номера документа отклоняются. Контроль качества (WMS-37) и претензии — отдельные блоки. |
| D-50 | Вкладки карточки проекта (PRJ-13/14/15/16, M.4) | Карточка проекта получает вкладки «Обзор», «Задачи», «Потребности», «Документы», «История». Отдельной таблицы истории проекта не заводится: источник правды — уже существующий `audit_log` (`entity_type='PROJECT'`), вкладка показывает зафиксированные события без переписывания и без второй копии данных. Подписи действий формирует сервер, клиент коды не переводит. «Обзор» показывает только реальные счётчики связанных записей (задачи, открытые/завершённые, потребности, документы, участники); проценты готовности не вычисляются и не показываются, пока методика не утверждена (PRJ-18, M.1/M.4). Вкладки «Этапы» и «Изделия» не реализуются до появления самих сущностей (PRJ-08/09) — вместо них пустых заглушек нет. Фильтр задач по статусу выполняется на сервере, а не в списке на клиенте. Права: неучастник без `projects:read_any` получает 403 на любой вкладке; документы дополнительно учитывают конфиденциальность и `documents:read_any`. Вкладки «Потребности» и «Документы» только читают — создание потребности и загрузка файла остаются в своих разделах. |
