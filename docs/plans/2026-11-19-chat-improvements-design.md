# Дизайн комплексного улучшения Chat и Task Chat

## Статус и основание

- Дата: 2026-11-19.
- Статус: согласовано к реализации поручением пользователя «реализуй» после представления продуктового объёма.
- Подход: единый дизайн и совместимые контракты, три проверяемых направления — список/UX, сообщения/файлы, уведомления/надёжность.
- Сохраняются разные API и серверные правила DIRECT/GROUP/PROJECT/TASK. Единый раздел Chat не превращается в единую неразличимую таблицу сообщений.

## Текущая основа

Task Chat уже имеет серверную историю, курсорную пагинацию, realtime, системные события, ответы, реакции, упоминания, read marks, typing, поиск, закрепления, per-task черновики и ERP-панель. DIRECT/GROUP/PROJECT используют отдельные Conversations API и поддерживают историю, realtime, уведомления и один файл в сообщении. Общий список чатов пока строится из полных списков разговоров, задач и проектов и не содержит поиска, счётчиков и превью.

Существующие миграции V30–V31 и DTO расширяются обратимо совместимым образом. Существующие права просмотра не становятся правами записи. Закрытая задача остаётся read-only, кроме отметки прочтения.

## Целевой пользовательский опыт

### Единый список

Пользователь видит DIRECT/GROUP/PROJECT/TASK в одном списке с названием, типом, последним сообщением, автором, временем, unread/mention badges и состояниями pin/mute/archive. Доступны поиск и фильтры по типу, непрочитанным и упоминаниям. Сортировка: закреплённые, затем последняя активность. Список загружается серверными страницами; поиск и фильтры выполняются на сервере в пределах прав пользователя.

На широком экране список остаётся слева при переключении разговоров. На узком экране работает явная навигация список → переписка → назад. Выбор Task Chat не подменяет единый список отдельным списком задач.

### Лента сообщений

Все чаты получают общий визуальный язык: автор и время, отличие собственных сообщений, разделители дат, ответы, реакции, упоминания, форматирование, read/delivery state и поиск. Task Chat сохраняет SYSTEM-события и ERP-контекст.

Позиция прокрутки сохраняется по разговору. Догрузка старых сообщений не вызывает скачок. Новое сообщение автоматически прокручивает ленту только у нижней границы или для собственного сообщения. Переход из поиска/упоминания загружает нужный диапазон и подсвечивает сообщение.

### Черновики и файлы

Черновик, ответ и выбранные файлы хранятся отдельно для каждого разговора в пределах жизни клиентской сессии. Поддерживаются несколько файлов, изображения с безопасным предпросмотром, вставка/выбор файлов, прогресс, отмена и повтор отправки. Идемпотентность сохраняется при повторе. Сервер проверяет количество, размер, допустимость содержимого и права на каждый файл.

### Изменение и пересылка

Автор может редактировать своё USER-сообщение в открытом чате; отображаются признак и время редактирования, прежние версии сохраняются на сервере. Отзыв заменяет содержимое нейтральным системным следом и не уничтожает аудит. SYSTEM-события не редактируются и не отзываются как обычные сообщения.

Пересылка создаёт новое сообщение с явными источником и автором исходника. Сервер независимо проверяет доступ к источнику, право записи в цель и доступ к каждому вложению. Недоступный источник не раскрывается через preview, поиск или realtime.

### Уведомления

Центр остаётся основным сохраняемым каналом. Service Worker обеспечивает внешний push при закрытой вкладке; payload нейтрален и не содержит текста сообщения, названий задачи/проекта или имён участников. Клик ведёт через аутентификацию и повторную проверку прав.

Пользователь может отключать обычные уведомления по разговору и настраивать упоминания отдельно. При запрете разрешения, отсутствии push или ошибке доставки центр продолжает работать без ложного подтверждения внешней доставки.

## Архитектура и контракты

### Серверная модель

Добавляются отдельные расширения для conversation messages и пользовательских состояний единого списка, не смешивающие их с task-chat таблицами:

- метаданные сообщения: ответ, редактирование, отзыв, источник пересылки;
- reactions, mentions и read states для DIRECT/GROUP/PROJECT;
- per-user pin/mute/archive и read cursor для единого списка;
- история редакций и служебные поля аудита;
- push subscriptions с endpoint/ключами, владельцем и состоянием отзыва.

Task Chat использует существующие таблицы V31; недостающие edit/revoke/forward и multi-file поля добавляются в его собственной модели. Общие DTO могут использовать одинаковые вложенные структуры (`ReplyPreviewDto`, `ReactionSummaryDto`), но идентификаторы и маршруты остаются типизированы по виду чата.

### Единый list API

Добавляется серверный агрегирующий endpoint списка с query, фильтром, cursor/limit. Он объединяет уже авторизованные проекции источников и возвращает стабильный составной ключ `(kind, id)`, preview, счётчики и пользовательские состояния. Не допускается сначала загрузить закрытые записи и фильтровать их только в памяти: ограничения прав участвуют в каждом источнике выборки.

Для DIRECT/GROUP/PROJECT последняя активность и счётчики вычисляются по conversation messages/read states. Для TASK используются task chat messages/read states и существующие основания доступа. Отзыв доступа исключает запись из списка, историю, realtime, поиск, файлы и push-переход.

### Сообщения и realtime

REST остаётся источником подтверждения команд и догона истории. WebSocket доставляет типизированные события создания, редактирования, отзыва, реакции, read state, typing и pin/state. Клиент после разрыва использует серверный курсор и догоняет пропущенное без дублей. Публикация происходит после commit.

Создание/редактирование/отзыв/реакции/пересылка и загрузка файлов — идемпотентные команды там, где повтор может создать или изменить содержимое. Сообщения и уведомления сохраняются атомарно с соответствующими метаданными. Добавляются серверные ограничения частоты и размеров.

### Push

Подписка привязана к пользователю и отзывается при выходе/деактивации. Сервер отправляет только нейтральное событие; клиент получает актуальные данные авторизованным API. Недействительные подписки удаляются. Нейтральность payload, права при клике и сохранность центра проверяются тестами. Конкретный Web Push provider/protocol выбирается из совместимых с текущим Ktor/Kotlin стеком без скрытого добавления зависимостей; если инфраструктурный VAPID-секрет не настроен, функция явно остаётся выключенной, а не имитируется.

## Обработка ошибок и граничные состояния

- Ошибка отправки не очищает черновик и файлы; доступен повтор с тем же idempotency key.
- 401/403/404 прекращают недопустимую подписку; отзыв доступа скрывает содержимое без утечки через старое состояние.
- 409 при конкурентном редактировании предлагает перезагрузить сообщение, не затирая чужую версию.
- Закрытая задача отклоняет все изменяющие команды единым бизнес-конфликтом.
- Пустой результат фильтра отличается от отсутствия доступных чатов.
- Ошибка одного источника единого списка не выдаёт неполную страницу за полную; пользователю показывается ошибка с сохранением уже загруженных данных.
- Поиск, счётчики, превью и push не раскрывают записи, ставшие недоступными.

## Адаптивность и доступность

Сохраняются существующие ERP theme и breakpoints. На desktop используется split workspace, на телефоне — list/detail. Все действия имеют текстовые labels/semantic descriptions, статус не кодируется только цветом. Поддерживаются Ctrl+Enter, Ctrl+F, Escape, клавиатурная навигация по результатам поиска и видимый focus.

## Проверка

### Сервер

- CRUD-команды сообщений, история редакций, tombstone отзыва и запрет изменения SYSTEM.
- Reactions/mentions/read/search для всех видов чатов.
- Многофайловая отправка, повтор без дублей, лимиты и отдельная авторизация скачивания.
- Единый список: сортировка, курсоры, фильтры, счётчики, отсутствие утечек и отзыв доступа.
- Realtime после commit, reconnect/cursor, изоляция пользователей и закрытая задача.
- Push payload, subscriptions, запрет разрешения и переход после входа/отзыва прав.
- Rate limiting и конкурентное редактирование.

### Клиент и браузер

- JS/Wasm-тесты фильтров, сортировки, черновиков, прокрутки, realtime merge и обработки ошибок.
- Реальные HTTP-сценарии двумя пользователями для DIRECT/GROUP/PROJECT/TASK.
- Браузерная проверка desktop/mobile, поиска, навигации назад, ответа/реакции/редактирования/отзыва, нескольких файлов и повтора отправки.
- Проверка закрытой вкладки для push выполняется только при настроенной push-инфраструктуре; иначе этот результат явно остаётся непроверенным.

## Документация и готовность

После каждого интегрированного пакета обновляются `docs/features.md`, `PROGRESS.md`, `TASKS.md` и при изменении утверждённых правил — `docs/decisions.md`. Функция отмечается DONE только после реальных проверок. Непроверенный внешний push или визуальный сценарий не выдаётся за завершённый.
