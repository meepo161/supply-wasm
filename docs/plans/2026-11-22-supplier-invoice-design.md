# Проект: документ «Счёт поставщика»

**Статус:** процесс «кто что делает» (раздел 1) и схема раздела 2 подтверждены пользователем 22.11.2026 — **D-61**. Остальное (модель, статусы, этапы) — предложение, **не утверждено**. D-55 прямо относит оплату и счета к работам вне объёма, D-18 и вопрос §35.9 ТЗ («учёт оплат или только передача в бухгалтерию») не решены. Реализация начнётся только после нового решения пользователя (см. «Решения, которые нужны»).

Пример для разработки — счёт ОАО «СЗТТ» № 219658 от 25.02.2025 (4 позиции трансформаторов ТОП/ТШП, 28 032,00 ₽ с НДС, 100 % предоплата, кратность 3). Сверка его полей с текущей моделью — в `docs/audit/2026-11-22-system-audit.md`, раздел «Сверка полей счёта поставщика».

## 1. Зачем нужен отдельный документ

Сейчас счёт существует только как текстовое поле `PurchaseOrder.invoiceNo` и как вид основания приёмки (`ReceiptSourceType.INVOICE`, номер строкой). Из-за этого:

| Проблема сегодня | Что даст «Счёт» |
| --- | --- |
| Не видно, что выставлено к оплате, что оплачено и что просрочено | Реестр счетов со статусом оплаты и сроком действия; виджет «К оплате на этой неделе» |
| Цены, количества и кратность в счёте никто не сверяет с заказом | Автоматическая сверка «счёт ↔ заказ ↔ приёмка» (трёхстороннее сопоставление) с понятными расхождениями |
| По 100 % предоплате поставщик начинает изготовление только после оплаты, а система не знает, что поставка ждёт денег | Связь «оплачено → срок изготовления пошёл»: ожидаемая дата поставки = дата оплаты + 25 рабочих дней |
| Нет банковских реквизитов: бухгалтерия перепечатывает их из PDF | Реквизиты в карточке поставщика + назначение платежа из счёта; экспорт реестра платежей |
| Счёт с истёкшим сроком (7 банковских дней) оплачивают по старой цене | Предупреждение и блокировка согласования истёкшего счёта |
| Номер счёта не ищется, PDF лежит отдельно | Поиск по номеру счёта и ИНН; PDF прикреплён к документу |
| Оценке поставщика (ТЗ §9.8) не хватает фактов о стабильности цены и сроках | История цен по счетам и фактические сроки «оплата → поставка» |

**Кто что делает (уточнено пользователем 22.11.2026).**

- **Снабжение — владелец счёта.** Снабженец получает счёт от поставщика и **обязательно загружает его файл** (PDF/скан). Счёта без файла не бывает. Затем снабженец сверяет счёт с заказом и **сам оформляет поступление на склад по счёту**: документ «Поступление по счёту» создаётся из карточки счёта во вкладке «Снабжение», строки и количества берутся из счёта.
- **Склад** не создаёт приёмку по счёту и не вводит номер счёта вручную. Кладовщик видит поступление, подготовленное снабжением, в очереди «Ожидается к приёмке», физически принимает товар, указывает фактическое количество и ячейки, фиксирует расхождения с обоснованием и проводит. Остаток появляется только после проведения (D-56).
- Руководитель или начальник снабжения согласует оплату. Бухгалтер (роль из ТЗ §3) видит реестр к оплате и отмечает оплату. Руководство видит кредиторскую задолженность.

## 2. Место в процессе

```
СНАБЖЕНИЕ                                                         СКЛАД
Потребность → Предложение → Выбор → Заказ поставщику
        ▼
Счёт поставщика: загрузка файла (обязательно) → строки → сверка с заказом
        ▼
Согласование оплаты (ApprovalService) → Оплата → срок изготовления
        ▼
«Поступление по счёту» (создаёт снабженец из счёта) ──────► очередь «Ожидается к приёмке»
                                                                   ▼
                                               физическая приёмка: факт, ячейки, расхождения
                                                                   ▼
                                                           проведение → остаток
        ◄────────── расхождения и брак возвращаются снабженцу (претензия поставщику)
```

Поддерживаются три реальных варианта:

1. **Предоплата** (как в примере): заказ → счёт → оплата → изготовление → приёмка.
2. **Постоплата**: заказ → поставка и приёмка → счёт → оплата в срок (например, 30 дней).
3. **Счёт без заказа** (срочная мелкая закупка): счёт регистрируется сразу и привязывается к заказу позже. По аналогии с `receipt_links` это журнал без перезаписи; согласование оплаты без заказа требует отдельного права.

К одному заказу может быть несколько счетов (аванс + окончательный, частичные поставки). Один счёт относится ровно к одному поставщику и, как правило, к одному заказу.

## 4. Модель данных (эскиз)

| Поле | Тип | Источник в примере |
| --- | --- | --- |
| `id`, `version` | BIGSERIAL, BIGINT | — |
| `number` | VARCHAR(64), обязательное | 219658 |
| `invoice_date` | DATE, обязательное | 25.02.2025 |
| `supplier_id` | FK `suppliers` | ОАО «СЗТТ» |
| `supplier_inn`, `supplier_kpp` | снимок из счёта | 6658017928 / 665801001 — сверяются с карточкой |
| `buyer_org_id` | FK `organizations` | ООО «АВИААГРЕГАТ-Н» — сверяется ИНН 6150045308 |
| `purchase_order_id` | FK, может быть NULL | Заказ клиента №219658 |
| `supplier_bank_account_id` | FK `supplier_bank_accounts` | Уральский банк ПАО Сбербанк, БИК, р/с, к/с |

| `lead_time_days` + `lead_time_kind` (`WORKING`/`CALENDAR`) | INT, VARCHAR | 25 рабочих дней |
| `delivery_terms` | TEXT | до ТК «Деловые Линии», тариф за покупателем |
| `payment_purpose` | TEXT | «Оплата по заказу клиента №219658» |

Уникальность: `(supplier_id, number, invoice_date)` для неотменённых счетов — защита от повторной регистрации.

### 4.2. `supplier_invoice_lines` — строки

| Поле | Пример |
| --- | --- |
| `line_no` | 1 |
| `supplier_item_code` | 10000185984 |
| `supplier_item_name` | ТОП-0,66-5-0,2S-120/5 У3 |
| `nomenclature_id` | наша номенклатура (сопоставление, см. §4.4) |
| `purchase_order_line_id` | строка заказа |
| `quantity`, `unit` | 3 шт |
| `unit_price` | 2 220,00 |
| `vat_rate` (`NULL` = «Без НДС») | 20 |
| `vat_amount`, `line_total` | 1 332,00 / 6 660,00 — **хранятся, как в документе** |

Суммы хранятся так, как напечатаны в счёте, а не только вычисляются. Система отдельно пересчитывает их с округлением до копеек по строке и показывает расхождение (п. 6). Так закрывается риск «копеечных» расхождений из сверки.

### 4.3. `supplier_invoice_payments` — оплаты (если выбран учёт оплат)

`invoice_id`, `paid_at`, `amount`, `payment_order_no` (№ платёжного поручения), `note`, `recorded_by`. Сумма оплат не может превышать `gross_total`; частичная оплата даёт статус `PARTIALLY_PAID`.

### 4.4. Справочники

- `supplier_bank_accounts`: банк, БИК, р/с, к/с, основной ли. Хранятся в карточке поставщика; изменение реквизитов фиксируется в аудите как рисковое событие (защита от подмены реквизитов).
- `organizations`: наша организация — наименование, ИНН, КПП, адрес, телефон. Нужна для сверки покупателя и для будущих печатных форм.
- `supplier_item_codes`: соответствие «код поставщика → наша номенклатура» для конкретного поставщика. После первого сопоставления строки следующих счетов сопоставляются автоматически.

### 4.5. Связи с существующим

- `receipts`: поле `supplier_invoice_id`; для основания `INVOICE` оно **обязательно**, а номер и дата документа-основания берутся из счёта, не вводятся вручную. Приёмку по счёту создаёт снабжение (право `invoices:create_receipt`) из карточки счёта. Склад получает её как черновик с ожидаемым количеством и проводит после физической приёмки (`wms:post`). Для уже проведённых приёмок — запись в `receipt_links`.
- `supplier_invoices.document_id` — **обязательный**: счёт нельзя зарегистрировать без загруженного файла.
- `documents` / `document_links`: PDF счёта со ссылкой на объект `SUPPLIER_INVOICE`.
- `purchase_orders.invoice_no` остаётся для совместимости и показывается как «номер первого счёта», затем выводится из таблицы счетов.
- `nomenclature.order_multiple` (V41): используется в сверке кратности.

## 5. Статусы

```
DRAFT ──► CHECKED ──► PENDING_APPROVAL ──► APPROVED_FOR_PAYMENT ──► PARTIALLY_PAID ──► PAID ──► CLOSED
  │          │               │                        │
  └──────────┴──── DISPUTED (расхождения, запрос поставщику) ◄─┘
  └──► CANCELLED (с причиной)          EXPIRED — истёк срок до оплаты (можно перевыставить)
```

- `DRAFT` — зарегистрирован, строки можно править.
- `CHECKED` — сверка выполнена: блокирующих расхождений нет либо они приняты с обоснованием.
- `PENDING_APPROVAL` / `APPROVED_FOR_PAYMENT` — через существующий `ApprovalService`: новый адаптер `SupplierInvoiceApprovalTarget` по образцу `PurchaseOrderApprovalTarget`. Маршрут, пороги и согласующие берутся из шаблонов согласования (§9.7 ТЗ, открытый вопрос — не выдумываются).
- `PAID` → `CLOSED` после полной приёмки по связанному заказу.
- Все переходы: версия объекта, ключ идемпотентности, аудит, как в заказах (D-55).
- Существенное изменение после согласования (сумма, реквизиты, получатель) возвращает счёт на согласование.

## 6. Сверка (что проверяет система)

| Проверка | Уровень |
| --- | --- |
| ИНН/КПП поставщика в счёте совпадает с карточкой | блокирует |
| ИНН покупателя совпадает с «Нашей организацией» | блокирует |
| Банковские реквизиты совпадают с подтверждёнными в карточке; новые реквизиты требуют подтверждения | блокирует |
| Повтор номера счёта у того же поставщика | блокирует |
| Количество по строке ≤ остатку заказа к оплате | блокирует, можно принять с обоснованием |
| Цена по строке совпадает с ценой заказа (допуск — настройка) | предупреждение или блокировка с обоснованием |
| Количество кратно `order_multiple` (ТОП/ТШП — кратно 3) | предупреждение |
| Пересчёт НДС и итогов с округлением по строкам совпадает с напечатанными | предупреждение с показом разницы |
| Срок действия: до истечения ≤ 2 банковских дней | предупреждение; после истечения согласование запрещено |
| Сумма счетов по заказу не превышает сумму заказа | блокирует |

Расхождение можно принять только с обоснованием. Оно попадает в историю и в оценку поставщика.

## 8. Ввод счёта: без ручной перепечатки

1. **MVP:** снабженец загружает файл счёта (обязательно) и заполняет шапку; строки по умолчанию копируются из заказа и правятся по файлу. Файл всегда открывается рядом с формой для сверки.
2. **Этап 2 — помощник распознавания.** У большинства счетов (включая пример) в PDF есть текстовый слой. Сервер извлекает номер, дату, ИНН/КПП, БИК, р/с, таблицу строк и итоги и предлагает черновик, который пользователь подтверждает. Сканы без текстового слоя — только вручную, OCR вне объёма.
3. **Этап 3 — интеграция с бухгалтерией** (после решения по D-18): выгрузка реестра платежей и приём отметок об оплате (формат 1С, CSV или иной — не выбран).

## 10. Решения, которые нужны от пользователя

1. Включаем ли счёт поставщика в объём (сейчас D-55: «оплата, счета-фактуры вне объёма»)?
2. Учёт оплат в ERP (отметка «оплачено», частичные оплаты) или только реестр «к оплате» для бухгалтерии (§35.9 ТЗ)?
3. Кто согласует оплату и есть ли суммовые пороги (§9.7 — открытый вопрос)?
4. Допуск по цене между счётом и заказом: 0 %, фиксированная сумма или процент?
5. Можно ли согласовывать оплату по счёту без заказа (срочные закупки) и кому?
6. Нужны ли валютные счета, или только рубли?
7. Счёт-фактура и УПД — отдельные документы на следующем этапе или пока остаются основанием приёмки (как в D-56)?
